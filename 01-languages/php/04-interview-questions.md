# PHP Interview Questions

## Easy

### Q1: What does `declare(strict_types=1)` do, and at whose scope does it apply?
**Answer:** It forces strict type checking at function call boundaries — `int` parameters will not accept a numeric `"1"` string. Crucially, strict types is determined by the **file containing the call site**, not the file declaring the function. A library cannot force its callers into strict mode; a caller without the directive merely coerces using PHP's normal juggling. It must be the very first statement in the file (no whitespace or `<?php` prior), and it scopes to that file only. Mixing libraries with and without strict types is fine because each call site adopts its own mode.

### Q2: What is the difference between value and reference semantics in PHP?
**Answer:** Scalars (`int`, `float`, `string`, `bool`) are passed by value — assignment copies. Arrays are also **value types** with copy-on-write: assigning an array creates a new array that diverges on mutation (this trips up interviewees who assume "arrays are objects"). Objects, on the other hand, are passed by handle: assigning or passing an object copies the **reference to the object**, not the object's state, so mutations through any alias are visible to all references. The `&` operator forces an explicit reference for any variable. `static` variables inside a function persist across calls but maintain per-function scope, not shared scope.

### Q3: How are PHP arrays structured internally, and what guarantees does that give you?
**Answer:** A PHP array is an ordered hash table mapping integer and string keys to zval (typed value) slots. Keys are normalized: numeric strings without leading zeros coerce to integers, floats truncate, `true`→`1`, `false`→`0`. Most importantly, **insertion order is preserved** during iteration — unlike a Java `HashMap`, you can rely on the order in which you inserted items. Access, insert, update, and existence check are amortized O(1). Copy-on-write means writing to one alias triggers a real copy only when needed, so passing arrays around is cheap until mutation. Arrays are not objects and have no methods; you use the `array_*` functional API instead.

### Q4: What is the difference between `self`, `static`, and `parent`?
**Answer:** `self::` is statically resolved to the class where the method is literally written (lexical), while `static::` is resolved at runtime to the class on which the method was actually invoked — this is **late static binding**. `parent::` refers to the parent of the class where the call is written, also lexical. The classic trap: in a base class `make()` returns `new self` produces a base class instance even when invoked as `Sub::make()`, whereas `new static` returns a `Sub`. Use `static` for factory methods and polymorphic construction; use `self` when you genuinely mean exactly this class.

### Q5: Compare `match` and `switch`.
**Answer:** `match` is an expression that returns a value, uses strict `===` comparison, supports comma-separated arms, has no fall-through, and throws `\UnhandledMatchError` when no arm matches and there's no `default`. `switch` is a statement using loose `==`, supports fall-through (which requires explicit `break`), and silently does nothing on no match. `match` is the default choice for value selection; `switch` retains niche value for fall-through side effects or multi-statement arms. Because `match` is strict, `match(0)` will NOT match `'0'` or `false` — this real difference is a common bug source when refactoring from `switch`.

### Q6: What is constructor property promotion?
**Answer:** Constructor property promotion (PHP 8.0+) collapses the boilerplate of declare-field, set-parameter, and assign-in-body into a single signature. A constructor parameter that has a visibility modifier (`public`, `protected`, or `private`) automatically becomes a property of the same name and visibility, and is assigned from the argument automatically. Since PHP 8.5, asymmetric visibility (`public private(set)`) on promoted parameters works too. This is the idiomatic way to author value objects: `public function __construct(public readonly string $id, public readonly string $email)` declares two readonly promoted fields. Only one constructor per class is allowed; default arguments express optionality.

### Q7: What is PSR-4 autoloading?
**Answer:** PSR-4 maps a fully-qualified class name to a filesystem path: the namespace prefix declared in `composer.json` corresponds to a base directory, and the rest of the namespace maps one-to-one to subdirectories, terminating in `<ClassName>.php`. So `Acme\Order\Service\Cart` with prefix `Acme\\` rooted at `src/` resolves to `src/Order/Service/Cart.php`. PSR-4 is path-based and works with one file per class. The classmap autoloader (`composer dump-autoload --optimize`) is the faster production form: a precomputed array maps every class name to its file, eliminating directory walks entirely on each request.

## Medium

### Q8: How do closures capture variables, and how does `$this` binding work?
**Answer:** A `Closure` (anonymous function) captures variables from the enclosing scope via an explicit `use` clause, by value by default and by reference with `&`. Arrow functions (`fn($x) => ...`) auto-capture by value without `use`, but only single expressions. `$this` is captured automatically inside a class context, and the closure is bound to that instance. `Closure::bind($closure, $newThis, $scopeClass)` returns a new closure rebound to a different object and scope (the scope controls access to private/protected members). This is how hydrators and serializers reach private fields, and why you must be careful passing closures across trust boundaries.

### Q9: When would you use generators vs arrays?
**Answer:** Generators (`yield`) are the right choice for streaming pipelines (often via libraries that abstract yield access), large result sets (line-by-line from a database), or lazy infinite sequences — they keep memory flat because they don't materialize the full result. They trade per-yield function-call overhead for memory savings. Arrays are the right choice when you need random access by index/key, multiple passes of iteration, or want to count/sort/aggregate the whole collection once. Generators cannot be indexed by position or iterated multiple times unless rewound explicitly (only once for plain generators), and they stop computation at the end of iteration.

### Q10: What are fibers, and how do they differ from generators?
**Answer:** A fiber (PHP 8.1+) is a stackful coroutine: a code block with its own call stack that can suspend itself from any depth of nested calls and be resumed later, while generators only suspend a single function frame. Fibers expose `->start()`, `->resume($value)`, `Fiber::suspend($value)`, `->getReturn()`, `->throw()`. They are not real OS threads — only one fiber runs at a time per process; they enable **cooperative concurrency** for an event loop to multiplex many in-flight I/O operations without blocking the thread. Generators are the higher-level tool for lazy iteration; fibers are the lower-level tool used by async frameworks (AMP v3, Revolt, Swoole) to give you synchronous-looking code inside an event loop.

### Q11: Explain enums and backed enums in PHP.
**Answer:** Enums (PHP 8.1+) are special class hierarchies rooted at `\UnitEnum`. Pure enums (`enum Status {}`) carry no scalar value; backed enums (`enum Status: string {}` or `: int`) attach a literal scalar to each case, useful for DB/API serialization. Cases are singleton instances: two `Status::Active` references are identical. `Status::cases()` returns all declared cases in declaration order; `Status::from('active')` throws `\ValueError` on miss, `Status::tryFrom('nope')` returns null. Enums can implement interfaces, use traits (stateless only), and have constants and methods — but **cannot** have instance state, be instantiated, cloned, serialized destructively, or have construct parameters. There is no native `fromName()` API; look up a case by name via `cases()` and `name` comparison.

### Q12: What does a generator look like, written idiomatically, to stream rows from a DB?
**Answer:**

```php
function streamUsers(PDO $pdo, int $batch = 1000): Generator {
    $lastId = 0;
    while (true) {
        // Keyset pagination: WHERE id > ? is index-friendly and stable.
        $stmt = $pdo->prepare('SELECT id, email FROM users WHERE id > ? ORDER BY id LIMIT 1000');
        $stmt->execute([$lastId]);
        $rows = $stmt->fetchAll();
        if (!$rows) return;
        foreach ($rows as $row) { yield $row; }
        $lastId = end($rows)['id'];
    }
}

foreach (streamUsers($pdo) as $user) { /* process one at a time */ }
```

This pattern only keeps one batch in memory at a time, regardless of the total table size. Memory stays flat even for millions of rows; the alternative `fetchAll()` would balloon. Note: with native prepared statements (`PDO::ATTR_EMULATE_PREPARES=false`, the recommended secure default), MySQL does not allow `LIMIT ?` placeholders — that's why keyset pagination (`WHERE id > ?`) is preferred over `LIMIT ? OFFSET ?`. For even better performance, prefer `fetchAll(PDO::FETCH_ASSOC)` over `FETCH_OBJ` to avoid per-row object allocation.

### Q13: Explain typed class constants and the `#[\Override]` attribute.
**Answer:** Typed class constants (PHP 8.3+) require each constant to have a type declaration: `public const int STATUS_OK = 200;` and the engine will reject a value of a different type at declaration time, catching mistyped constants like `'200'` early. Interface constants can be typed too. The `#[\Override]` attribute (8.3+), placed on a method, asserts that the method overrides a parent method; if the parent signature disappears due to a typo or refactor, the engine raises a compile-time fatal error — catching the mistake at compile time. Both are static-analysis-friendly additions that intercept common maintainer errors.

### Q14: What are readonly properties and a readonly class, and is readonly the same as immutability?
**Answer:** `readonly` (8.1 properties, 8.2 classes) blocks writes to a property after initialization: assignment is only allowed from within the declaring class's scope, in practice the constructor. Promoted readonly properties are the canonical form. A `readonly class` makes all instance properties readonly and disallows dynamic properties. As of PHP 8.3, readonly properties can be re-initialized once during `__clone` (the "readonly amendment" RFC), enabling some clone-with-modification patterns. **Readonly is not full immutability**: a readonly property holding an object reference still allows mutations of the inner object's mutable fields; readonly guards the *reference*, not deep state. True immutability in PHP needs `readonly` plus a value-object class hierarchy where every field is itself a readonly value type.

### Q15: What are property hooks (8.4) and asymmetric visibility (8.5)?
**Answer:** Property hooks (8.4) let you intercept get and/or set on a property right at its declaration, removing most boilerplate getter/setter code. A `get` hook is an expression `{ get => expr; }` and a `set` hook can validate or transform the value before storing it. "Virtual" hooks (no backing field) compute on each access. Asymmetric visibility (8.5) lets you declare that the *write* scope of a property is narrower than the read scope: `public private(set) string $id` allows anyone to read but only the declaring class to write. Combined, you can express the classic "publicly readable, privately writable, validated on write" shape declaratively, with no custom getter/setter boilerplate.

### Q16: Comparing traits, interfaces, and abstract classes — what goes where?
**Answer:** Interfaces express **capability contracts** — `Comparable`, `Iterator`, `Stringable` — and a class can implement many. Abstract classes express **partial implementation under an is-a relationship** — single inheritance, can carry concrete methods and state. Traits are **compiler-level horizontal code reuse** — methods are copy-pasted into the using class at compile time; multiple traits can be used; conflicts resolved with `insteadof`/`as`. Use interfaces for contracts, abstract classes for shared skeleton inheritance, and traits for shared method bodies that don't fit the type hierarchy. Avoid putting state (properties) in traits — collision semantics on property names across multiple traits are subtle and error-prone. Treat trait methods as stateless helpers.

### Q17: What are union, intersection, and DNF types?
**Answer:** Union types (`A|B`, PHP 8.0+) accept a value that is either `A` or `B`; scalar literals `null` and `false` are also allowed as union members (and `never` is a special return type, not a parameter type). Intersection types (`A&B`, 8.1+) require a value that implements **both** `A` and `B` simultaneously — only class/interface types, no scalars, no `null`. DNF types (8.2+) are disjunctive normal form: a union of parenthesized intersections, like `(HasId&HasName)|AnonymousGuest`. DNF lets you express "either this combination of interfaces, or that one" in a single type signature. Variance follows the usual subtyping rules: parameters are contravariant, returns covariant.

### Q18: What is dependency injection, and what role does a service container play?
**Answer:** Dependency injection is the practice of passing a class its collaborators through its constructor (or setters / methods) rather than letting the class instantiate them with `new`. This decouples the class from specific implementations and makes it testable — you can inject a fake. A service container (DIC, PSR-11 `ContainerInterface`) is the central wiring component at the composition root that knows how to instantiate services, resolve constructor dependencies by type (autowiring), manage singleton vs per-request scopes, and provide aliases. Production containers (Symfony DI, PHP-DI, Laravel) compile to fast PHP files. The cardinal sin of DI is calling `new` deep inside business logic — that hardcodes a dependency and hides the cost.

### Q19: How does PSR-4 autoload performance compare to a classmap?
**Answer:** PSR-4 uses filesystem path-to-namespace rules computed on demand; each autoload does a directory traversal cost unless OPcache has cached the resolved path. `composer dump-autoload --optimize` produces a **classmap**, an array mapping every class name to its file, eliminating directory walks. `--classmap-authoritative` makes the classmap the only source — unknown classes fail to autoload rather than fall back to PSR-4 lookup. `--apcu` caches the classmap in APCu to skip even the opcache lookup per request. In production this can shave off tens of milliseconds per request on big code bases; for CI/deploys it's essentially required. In dev, leave PSR-4 plain so newly added classes autoload without a re-dump.

### Q20: What does OPcache do, and what settings matter most for production?
**Answer:** OPcache caches compiled opcodes (the bytecode) in shared memory and serves cached bytecode on subsequent hits, eliminating the per-request parse/compile pass. Critical production settings: enough `opcache.memory_consumption` to fit all scripts, `opcache.max_accelerated_files` exceeding your script count (PHP rounds up to a prime), **`opcache.validate_timestamps=0`** to stop per-request `stat()` syscalls, with cache clearing tied to deploy (FPM restart or `opcache_reset()`), and `opcache.file_cache` to persist bytecode to disk for containers and CLI jobs. Monitoring `opcache_get_status(false)['memory_usage']`'s `used_memory`/`free_memory` ratio catches undersized `memory_consumption`. OPcache is per-host shared memory; it cannot persist across servers or different PHP binaries.

## Hard

### Q21: Walk me through the PHP request lifecycle under FPM and what "shared-nothing" means for application design.
**Answer:** A request arrives at the web server (nginx), which forwards via FastCGI to an idle FPM worker. FPM picked the worker from its pool (static/dynamic/ondemand); the request triggers per-request module init (`rinit`), PHP compiles + executes the entry script (using cached bytecode from OPcache), the application runs, the response is flushed back over FastCGI, and per-request shutdown (`rshutdown`) frees all request-local memory. Worker returns to the pool. "Shared-nothing" means each request effectively starts from a clean global state: superglobals are fresh, static fields are fresh (unless OPcache-preloaded or persistent across the worker's lifetime), autoloaded classes are reloaded from OPcache (fast) but were never kept in app-state form between requests. The implication: you cannot rely on a global Long-lived application object holding state across requests — use APCu, Redis, or a database for things that must outlive a request. This is the architectural property that makes PHP scale horizontally with simple semantics but also why long-running daemon patterns need a different mental model.

### Q22: How does the JIT work, and when does it actually matter?
**Answer:** The JIT (PHP 8.0+, via DynASM in ext-opcache) compiles hot opcodes to native machine code in a JIT buffer (`opcache.jit_buffer_size`). The default mode since 8.4 is "tracing" JIT, which collects execution traces through loops and specializes them. JIT helps **CPU-bound, tight-loop code**: numerical algorithms, image manipulation, template engines parsing heavy templates, regex-heavy text processing. It does **not** meaningfully speed up I/O-bound request handlers — most web app time is in DB, network, and templates that fit in OPcache; the bytecode compilation cost is already gone with OPcache. Tune `opcache.jit_buffer_size=64M..256M`; the mode `1205` (tracing) is the sensible default. Always benchmark with realistic traffic: enabling JIT can occasionally *slow* an I/O-bound application if the buffer and warm-up cost outweigh gains. Profile before and after using a sampling profiler (Tideways or Blackfire).

### Q23: Explain FPM worker tuning — how would you size `pm.max_children`?
**Answer:** Workers are OS processes; each holds a full PHP interpreter, OPcache arena share, plus per-request allocations. Start with the formula `max_children ≈ (total_RAM − headroom) / per-request_peak_RAM`. Measure per-request peak memory with `memory_get_peak_usage(true)` on representative traffic — a typical Symfony app sits at 30-80 MiB, Laravel at 20-60 MiB, a heavy Doctrine row set 100+ MiB. Then size `max_children` so that `max_children * peak_memory < total_RAM` after you account for OPcache shared memory (~256 MiB), APCu if present, the master process, and the OS. If workers saturate RAM, you get OOM kills, not graceful degradation — the cardinal failure mode. For CPU-bound work, more workers help until the CPU saturates; for I/O-bound work, more workers help until disk or DB saturate, then you need async frameworks (Swoole, FrankenPHP persistent mode) rather than more children. Set `pm.max_requests=1000` so workers cycle and release memory leaks to the OS.

### Q24: How do you defend against SQL injection? Show vulnerable vs secure.
**Answer:** Vulnerable code interpolates user input into the SQL text — even with `addslashes`, which doesn't understand context. Secure code uses prepared statements with **bound parameters**:

```php
// Vulnerable:
$pdo->query("SELECT id FROM users WHERE email = '" . $email . "'");

// Secure:
$stmt = $pdo->prepare('SELECT id FROM users WHERE email = ?');
$stmt->execute([$email]);
$uid = $stmt->fetchColumn();
```

Set `PDO::ATTR_EMULATE_PREPARES=false` so the DB server handles the prepare and the parameter placeholders are real, not emulated client-side. For values that **cannot** be parameterized (column names, sort directions, `IN` lists where you must interpolate the placeholder count), use an allowlist: validate against `['asc','desc']` or `array_keys` of known columns and only then interpolate the known-safe token. ORM query builders parameterize under the hood; raw helpers like Laravel's `DB::unprepared()` or Doctrine `NativeQuery` with concatenated SQL bypass parameterization — keep raw SQL fragments out of user-controlled paths.

### Q25: What is XSS and how do you defend against it context-aware?
**Answer:** XSS is injecting HTML/script into the page such that the browser executes it. The defense is **context-aware output encoding**. In an HTML body context, escape with `htmlspecialchars($s, ENT_QUOTES | ENT_SUBSTITUTE | ENT_HTML5, 'UTF-8')` — `ENT_QUOTES` is non-negotiable because it covers single-quoted attributes too. In attribute, body, and comment contexts the same function works. In a `<script>` block, **don't embed user data directly** — pass it via data attributes or use `json_encode` with `JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT` for safe insertion into script-block strings. In URL attributes, validate the scheme against an allowlist (`http`, `https`, `mailto`) and reject `javascript:`. For CSS, escape with `\\HHHHHH`. Modern template engines (Twig, Blade) auto-escape HTML by default; resist the urge to use `|raw` unless you know the context rules. Defense-in-depth with a `Content-Security-Policy` script allowlist (`script-src 'self' 'nonce-...'`) limits damage if an XSS slips through.

### Q26: How do you prevent CSRF?
**Answer:** Three layers stack: (1) **SameSite cookies** — `Lax` blocks most CSRF on POST while preserving top-level navigation; `Strict` is stricter but breaks legit cross-site flows. (2) **Anti-CSRF tokens** — generate a per-session random token, embed it in the form as a hidden field, compare the submitted value against the session-stored value using `hash_equals` (constant-time) — never use `==`. (3) **POST-only state changes** and `Origin`/`Referer` header checks as defense-in-depth. Tokens must rotate on privilege change (e.g., on login) to prevent fixation of a token onto a victim. Token strategies can be per-form with a CSRF library that ties the token to the originating form/page; double-submit cookies are a stateless alternative. SameSite alone is robust against classical CSRF but vulnerable to subdomain cookies and same-site cross-app attacks; tokens remain necessary.

### Q27: How do you hash passwords correctly in PHP?
**Answer:** Use `password_hash($plain, PASSWORD_DEFAULT)` and `password_verify($input, $hash)`. The default algorithm in most builds is bcrypt with auto-generated salt and a 10-12 cost factor; Argon2id (`PASSWORD_ARGON2ID`) is available if libsodium/argon2 is built and is memory-hard, recommended when you control the deployment. **Never** use MD5, SHA1, or plain SHA-256 — they're too fast for offline attackers. Bcrypt truncates at 72 bytes; for arbitrary-length passwords (e.g., passphrases) HMAC-SHA-256 the input first, then bcrypt the binary output — this also lets you apply a server-side pepper. Call `password_needs_rehash($hash, PASSWORD_DEFAULT, $newCost)` after a successful verify to upgrade the hash on next login as cost factors change. Rate-limit failed attempts at the IP/session boundary as an additional defense; hashing is for the case when the database leaks, rate limiting is for online guessing.

### Q28: What is session fixation and how do you address it?
**Answer:** Session fixation is an attacker supplying the victim with a known session ID (e.g. via a URL with `?PHPSESSID=...`). If the server accepts that ID without rotating it on privilege change, the attacker shares the session post-login. Defense stack: `session.use_strict_mode=1` rejects session IDs the server hasn't issued, the `secure`/`httponly`/`samesite=Lax` cookie flags prevent trivially leaking the cookie, and critically `session_regenerate_id(true)` is called on every privilege promotion (login, role change, password change) so a post-login session has a brand-new unknown-to-the-attacker ID. Out-of-the-box `session_set_cookie_params` defaults are **not** sufficient — they default to no `Secure` or `SameSite`. Always configure the cookie params explicitly in production, and store sessions in a shared backend (Redis/Memcached) behind TLS so multi-node deployments actually work.

### Q29: What are the risks of `unserialize()` of untrusted data?
**Answer:** `unserialize` instantiates arbitrary classes named in the payload and calls `__wakeup`/`__unserialize` on them, which can chain into "gadget chains" present in the project's vendor tree to achieve remote code execution. It is **RCE-equivalent on untrusted input**. Canonical mitigation: use `json_decode` for cross-boundary data interchange instead — JSON has no concept of class instantiation. If you must use `serialize` (e.g., a cache backend), pass `['allowed_classes' => false]` to disable class instantiation, or `['allowed_classes' => [SafeDto::class]]` to allowlist specific classes. Even with the allowlist, configure signed payloads via `hash_hmac` so transport is integrity-checked. Internal objects passed within one trust domain can be serialized safely; crossing any untrusted boundary, you must assume the payload is attacker-controlled.

### Q30: What is the N+1 query problem, and how would you fix it in a Laravel or Doctrine app?
**Answer:** N+1 is fetching a list with one query, then issuing one query per row to load a related association via lazy loading. The fix, in order of preference: (1) write a JOIN in SQL so one query loads the list and its relations; (2) two queries — load the list, then a second `WHERE foreign_id IN (?, ?, ?)` query to fetch all related rows, indexed by foreign key into an array for O(1) lookup; (3) eager loading at the ORM layer — Laravel's `$query->with('posts')` or Eloquent `$user->load('posts')`, Doctrine's `->matching(Criteria::where(...))` with batching or a `query_builder` join. Detect N+1 either by query log inspection (a tiny test asserting "1 base + 1 IN query, not 1 + N"), profiling with Tideways or DBAL query log, or static guardrails via lazy-loading blockers (Laravel's `Model::preventLazyLoading()`). Many ORMs default to lazy loading; opt in to eager loading at the right boundary (controller/repo) where the shape of the data is known.
