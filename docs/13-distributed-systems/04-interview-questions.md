## Distributed Systems Interview Questions

Use these for self-testing after the first three files. The grading skews deliberately senior/staff: the early questions establish the vocabulary a senior candidate must produce fluently; the later ones are the scenario probes staff loops use to test whether the concepts survive contact with an incident. Answer out loud before reading the model answer — at this level, precise language ("linearizable," not "strongly consistent"; "at-least-once plus idempotent effects," not "exactly-once") is a large part of the score.

## Senior baseline

### Q1: Why can't you rely on wall-clock timestamps to order events across machines?

**Answer:** Because each machine's time-of-day clock is an independent instrument: NTP sync over real networks is only good to tens of milliseconds (worse under congestion), clocks skew at different rates between syncs, and NTP corrections can step a clock backward. A paused VM simply loses time. So `t1 < t2` across two machines tells you nothing reliable about which event actually happened first — and systems that use wall clocks to decide conflicts (last-write-wins in Cassandra, for example) will silently drop writes from the node whose clock runs behind. Ordering across machines needs either causality tracking (Lamport/vector clocks, or hybrid logical clocks as in CockroachDB), a single serialization point (a leader's log, a Kafka partition), or hardware-bounded clock uncertainty that you explicitly wait out (Spanner's TrueTime). The honest summary: clocks are fine for TTLs, metrics, and humans; they are not fine for correctness decisions between machines.

### Q2: Explain happens-before, and the difference between Lamport clocks and vector clocks.

**Answer:** Happens-before is Lamport's causal order: `a → b` if they are in the same process with `a` first, if `a` is a message send and `b` its receipt, or by transitivity. Events with no happens-before path in either direction are concurrent — there is no fact of the matter about which came "first." A Lamport clock is a single counter (increment locally; on receive, take the max and increment) that guarantees `a → b ⇒ L(a) < L(b)`, so it produces a total order consistent with causality — but the converse fails, so it cannot tell you whether two events were concurrent. A vector clock keeps one counter per process, and comparison recovers causality exactly: one vector dominates the other iff the events are causally ordered; if neither dominates, the events are concurrent. That concurrency detection is why Dynamo-style stores use version vectors to surface conflicting siblings instead of guessing a winner, and the cost is O(N) metadata per value.

### Q3: Linearizability vs serializability vs sequential consistency — define all three and give a system for each.

**Answer:** Linearizability is a real-time, single-object guarantee: every operation appears to take effect atomically between its invocation and response, so once anyone reads a new value, everyone does — etcd's default reads, a lock service, DynamoDB's strongly consistent reads. Serializability is a multi-object transaction isolation guarantee: the result equals some serial order of transactions, with no promise that the order matches real time — a single-node Postgres running `SERIALIZABLE`. Sequential consistency is weaker than linearizability: all processes see the same total order, respecting each process's own program order, but not real-time order across processes — ZooKeeper's default reads are roughly this (writes are linearizable; reads can be slightly stale but ordered). Serializability plus linearizability is strict serializability — Spanner's target. The trap the question tests: "serializable" does not imply "fresh," and "linearizable" says nothing about multi-key transactions.

### Q4: What does R + W > N buy you in a Dynamo-style store, and what does it not buy you?

**Answer:** With N replicas per key, W write acks, and R read responses, R + W > N guarantees every read quorum overlaps every write quorum in at least one node, so a read sees the most recent acknowledged write with high probability — and you can tune per operation (W=2/R=2 balanced; W=3/R=1 read-heavy). What it does not buy: linearizability. Sloppy quorums — writes accepted by fallback nodes with hinted handoff during an outage — break the overlap guarantee entirely; concurrent writes still conflict and need version vectors or LWW to resolve; and a read racing a partial write can produce non-monotonic results across clients unless read repair is synchronous. Also worth saying: quorum reads pay the latency of the slowest of R nodes, and cross-datacenter QUORUM is why Cassandra deployments run LOCAL_QUORUM. The honest sales pitch is "very fresh, very available, probabilistic" — not "consistent."

### Q5: Why is `hash(key) mod N` a bad way to assign keys to nodes, and what do you use instead?

**Answer:** Because N appears in the formula: adding or removing one node changes the placement of almost every key. For a cache tier that means a near-total miss storm and a database stampede on every resize; for a storage tier it means migrating nearly the whole dataset. Consistent hashing fixes this by placing nodes and keys on a hash ring, with each key owned by the next node clockwise — a topology change moves only ~1/N of the keys. Production implementations add virtual nodes (each physical node claims many ring positions) to smooth load variance and spread a dead node's keys across many successors, and take a key's N replicas as the next N distinct physical nodes on the ring. Alternatives worth naming: rendezvous hashing (highest `hash(key, node)` wins — no ring, great in client libraries), jump hash (O(1), but buckets can only grow at the end), and Maglev (load-balancer lookup tables). The fixed-partition alternative — many more partitions than nodes, moved whole, as in Kafka or Redis Cluster's 16384 slots — achieves the same goal by never re-hashing at all.

## Senior

### Q6: Walk me through how Raft elects a leader and why split-brain is impossible in it.

**Answer:** Followers expect heartbeats from the leader; if a randomized election timeout (say 150–300 ms) expires, a follower increments the term, becomes a candidate, votes for itself, and requests votes. Peers grant at most one vote per term, and only to candidates whose log is at least as up-to-date as their own (compare last entry's term, then length). A candidate with a majority becomes leader and heartbeats; split votes time out and retry with new randomized timeouts, which is what makes elections converge. Two leaders in the same term are impossible because each node votes once per term and a majority is required — two majorities in one term would have to share a voter. Two leaders across terms can transiently exist (an old leader that has not heard the news), but the stale one is harmless: every RPC carries the term, any node seeing a higher term steps down, and a stale leader can never commit because committing requires a majority, and a majority has moved on. The follow-up worth pre-empting: leader reads still need ReadIndex, a log round, or a lease to be linearizable, because a deposed leader can serve stale reads before it learns it was deposed.

### Q7: What is a fencing token, and what class of bug does it fix that a lock service alone cannot?

**Answer:** A fencing token is a strictly increasing number issued with every lock grant or leadership term — etcd's revision, ZooKeeper's zxid, Raft's term, Kafka's epochs — that every protected resource checks, rejecting writes carrying a token older than the highest it has seen. It fixes the stale-holder bug that no lock service can prevent: a client acquires the lock, then pauses (GC, VM migration, long I/O) past its lease expiry; a new client acquires the lock and proceeds; the old client resumes and fires its write, fully believing it still holds the lock. The lock service was correct the whole time — the client's knowledge was stale, and there is no way to atomically check-and-act across a network. The only fix is for the resource itself to enforce ordering, via conditional writes (`UPDATE ... WHERE fence < :token`, DynamoDB condition expressions, S3 conditional PUTs). Two corollaries: a lock without downstream fencing is only an efficiency lock, and fencing requires the storage layer to support compare-and-set — if it cannot, no lock architecture makes the system safe.

### Q8: Your service uses a Redis `SET NX PX` lock around a nightly billing job. What can go wrong, and when is that acceptable?

**Answer:** Failure modes: (1) the job outlives the TTL — the lock expires mid-run and a second instance starts, so you have concurrent billing runs; (2) releasing without checking ownership — a bare `DEL` lets an instance whose lock already expired delete the *new* holder's lock, so release must be a Lua compare-token-and-delete; (3) Redis failover — with async replication the lock key may not have reached the promoted replica, so two holders exist; (4) the paused-client problem — even with correct TTLs, a GC pause makes the client act on a lock it no longer holds, and Redis issues no fencing token to catch it. This is acceptable exactly when the lock is for efficiency: if a duplicate billing run is prevented from double-charging by deeper idempotency — a unique constraint per `(account, billing_period)`, idempotency keys on the payment calls — then the lock only avoids wasted compute, and single-Redis is fine. If the lock is the *only* thing preventing double charges, the design is wrong regardless of Redis vs Redlock vs etcd: correctness needs idempotent effects and fencing at the data layer, not a better lock.

### Q9: "Our Kafka consumer is exactly-once because we enabled idempotence and transactions." Critique this claim.

**Answer:** Kafka's idempotent producer removes broker-side duplicates from producer retries, and transactions make consume-transform-produce atomic across Kafka topics for `read_committed` consumers — so within a Kafka-to-Kafka pipeline (Kafka Streams EOS), effectively-once processing is real. The claim breaks the moment the consumer touches anything outside Kafka: if it writes to MySQL and then commits its offset (or vice versa), a crash between the two produces a duplicate or a loss, and Kafka's transaction cannot span the external database. Exactly-once delivery is impossible in general — an ack loss is indistinguishable from a processing loss — so the achievable property is at-least-once delivery plus idempotent effects. Concretely for this consumer: store the processed offset (or message ID) in the same MySQL transaction as the state change, or dedup on a message-ID unique constraint, or make the write naturally idempotent. On the producer side, the mirror-image bug is dual-writing DB + Kafka without an outbox. The one-liner: Kafka gives exactly-once semantics inside its boundary; end-to-end, you build it out of idempotency.

### Q10: Compare 2PC and sagas for an order flow spanning payments, inventory, and shipping services. When would you still choose 2PC?

**Answer:** 2PC gives real atomicity — prepare, then commit/abort everywhere — but it is blocking: participants hold locks between prepare and the coordinator's decision, and a crashed coordinator strands them in-doubt with locks held. Across independently deployed microservices it also demands XA support and couples everyone's availability, which effectively disqualifies it there. A saga runs the flow as local transactions with compensations (refund, release reservation), either orchestrated (Temporal, Step Functions — explicit state, retries, timeouts first-class) or choreographed via events. The saga price is no isolation: intermediate states are visible, so you use semantic locks (`PENDING` status), commutative operations, and pivot ordering — put the non-compensatable step (capturing the payment, sending the confirmation email) after everything that could force a rollback; and every step and compensation must be idempotent because it will be retried. When 2PC is still right: inside a single system boundary under one operator, coordinated by consensus — Spanner and CockroachDB run 2PC over Raft/Paxos groups, which removes the coordinator SPOF — or a short-lived transaction between two resources you fully control where lock hold time is tiny. Across team-boundary microservices: saga, essentially always.

### Q11: Design the retry policy for a service that calls a flaky downstream. Go beyond "exponential backoff."

**Answer:** First classify: retry only errors that can plausibly succeed (timeouts, 503, connection reset), never deterministic failures (400/401/422), and only operations that are idempotent or made so with idempotency keys. Then: exponential backoff with full jitter — `sleep(random(0, min(cap, base·2^attempt)))` — because unjittered backoff re-synchronizes clients into waves. Cap total attempts and, more importantly, adopt a retry budget: retries as a ratio of primary traffic (say ≤10%, Envoy-style), so a real outage cannot multiply fleet-wide load; and retry at one layer of the stack — three retries at each of four layers is 3⁴ = 81x amplification at the bottom. Propagate deadlines so you never retry work the end client has already abandoned. Wrap it in a circuit breaker (open on error-rate threshold, half-open probe, close on success) with a per-endpoint fallback — stale cache, default, or queue-for-later. Server side, prefer early rejection (429/503 with `Retry-After`) over slow collapse. And instrument it: retry rate and breaker state are leading incident indicators; a silent retry storm looks like "traffic mysteriously tripled."

### Q12: What is a gray failure, and why do standard health checks miss it? What would you do instead?

**Answer:** A gray failure is degradation without death: a disk that makes every twentieth read take two seconds, 5% packet loss, a NIC at 100 Mbps, one slow shard. The defining property is differential observability — the system's own detectors say healthy while clients experience failure — so a `/health` endpoint that returns 200 keeps the node in rotation and the orchestrator routes users straight into the degradation; worse, naive automation can "remediate" the wrong node. Countermeasures: health checks that exercise the real dependency path (deep checks, used carefully — deep checks that fan out can themselves cascade); client-side signals as the source of truth, i.e., outlier ejection à la Envoy, ejecting upstreams whose latency/error profile deviates from the pool; peer-relative comparison (this node vs its siblings) instead of absolute thresholds; and hedged requests to route around slow replicas for idempotent reads. Finally, make automated remediation conservative — rate-limited, with hysteresis — because the failure detector is exactly what a gray failure fools.

### Q13: Why do tail latencies dominate at scale, and name three concrete techniques from "The Tail at Scale."

**Answer:** Fan-out arithmetic: if one server's p99 is 1 s, a request touching 100 servers experiences ≥1 s on 1 − 0.99¹⁰⁰ ≈ 63% of requests — the tail becomes the median of the composed system. The causes are mundane and unavoidable in aggregate: GC pauses, queueing, compaction and flushes, noisy neighbors. Techniques: (1) hedged requests — send to one replica, and if no reply by ~p95, duplicate to a second and take the first answer; a few percent of extra load buys a large tail cut, valid only for idempotent work, and cancel the loser; (2) tied requests — enqueue on two servers that know about each other, first-to-start cancels the twin, which beats hedging when queueing delay dominates; (3) micro-partitioning with selective replication — many small partitions per node so load rebalances in fine grains, plus extra replicas of hot data. Add the measurement discipline: SLOs on user-visible percentiles, never averages, and never averaging percentiles across hosts. This question doubles as a maturity probe: candidates who have run large fan-out systems recognize the 63% instantly.

## Staff

### Q14: Two services double-charged a customer. Walk me through the plausible causes, how you'd confirm which one it was, and the fixes.

**Answer:** Structure the hunt along the request path, one hypothesis at a time:

1. **Client/gateway retry without idempotency.** The charge call timed out (but succeeded); the caller retried; the payment API treated the retry as a new charge. *Confirm:* two charges with different request IDs seconds apart; gateway logs showing a timeout then a retry; the first response never delivered. *Fix:* an idempotency key minted per logical payment (not per attempt), stored atomically with the charge, response replayed on retry — plus a request-hash check so key reuse with a different amount is rejected, not replayed.
2. **Queue redelivery.** A worker consumed "charge customer," charged, then crashed before acking; the broker redelivered at-least-once and a second worker charged again. *Confirm:* broker redelivery count > 1 for that message ID; two charges bracketing a worker restart or rebalance. *Fix:* idempotent consumer — record the processed message ID in the same transaction as the charge, or enforce a unique constraint on `(order_id, charge_type)`.
3. **Saga or compensation bug.** A step failed *after* the charge and the saga retried from the top, or a refund compensation silently failed. *Confirm:* the orchestrator's execution history. *Fix:* durable orchestration (Temporal/Step Functions) with idempotent steps and compensations, and pivot ordering — capture the payment after all abortable steps.
4. **Dual writers.** A reconciler cron and the online path both "ensure the charge exists" from different views of the data — e.g., replica lag hid the first charge from the cron. *Confirm:* two different writer identities in the audit trail. *Fix:* a single writer per effect, or conditional writes/fencing so the second writer's attempt bounces.

Then the staff-level close: refund and customer comms immediately; a daily reconciliation diffing our ledger against the PSP to catch the *class*, not the instance; and one durable invariant — every money movement carries a unique business key enforced by the datastore — so any future duplicate is rejected at the last line of defense rather than by good behavior upstream.

### Q15: Implement a distributed rate limiter: 1,000 requests/minute per API key, enforced across a fleet of 50 gateway instances. Design it, then tell me what happens when your limiter's backing store fails.

**Answer:** Requirements first: accuracy tolerance (is 5% overage acceptable?), added latency budget (~1 ms), burst policy, and the failure stance — these determine the design more than the algorithm does.

- **Baseline: a token bucket per key in Redis, as a Lua script.** Read `(tokens, last_refill)`, refill at rate/60 per second up to burst capacity, decrement or reject, write back with a TTL. Lua makes the read-modify-write atomic without locks; hash-tag the keys so Redis Cluster keeps each key's state on one shard. Exact, simple, one round trip.
- **Cheaper when approximate is fine: sliding window counter.** Two fixed-window counters, the previous window weighted by overlap — smooths the boundary burst of fixed windows at a fraction of the memory of a sliding log.
- **At tighter latency or larger scale: local-first.** Each gateway enforces from an in-memory bucket against a locally cached allowance and syncs consumption asynchronously — or a coordinator hands out quota slices (50 instances × 20/min, rebalanced by observed skew). This trades exactness for zero added latency and store-outage tolerance. Bound the error and say the bound out loud: worst case ≈ one sync interval of overage × instance count.
- **Hot keys:** one enormous API key hotspots a single Redis shard — salt the bucket into k sub-buckets and check a random one, accepting bounded error.

Store failure is a policy decision, not an accident. **Fail-open** (limits off) protects availability — right for revenue traffic, wrong if the limiter is a security/abuse control. **Fail-closed** (reject) is the reverse. The best middle: **fall back to local-only enforcement**, each instance allowing quota/50, degrading accuracy instead of either availability or protection. Whichever you choose, alarm on it — a rate limiter silently failed-open is how you discover your capacity planning was load-bearing.

### Q16: Your MySQL primary failed over automatically, and afterward customers report missing orders that they received confirmation emails for. Explain what happened and how you'd redesign.

**Answer:** This is asynchronous-replication failover loss. The old primary committed the orders and the app returned 200 and queued the emails, but the binlog events had not reached the replica when the failover controller promoted it. The new primary has no such rows; the old primary's extra committed transactions are discarded on rejoin — or worse, it briefly kept accepting writes (split-brain) if promotion did not fence it. *Confirm:* diff the old primary's binlog position against the promoted replica's applied position, and audit the controller's timeline. Redesign in four layers:

1. **Replication mode.** Semi-sync (the primary waits for at least one replica ack before commit) or quorum-committed replication (Group Replication / Raft-based MySQL) so an acknowledged commit survives any single node's loss, at a fraction of write latency.
2. **Fencing on failover.** The controller must make the old primary unable to accept writes *before* promoting: set read-only, kill connections, revoke at the proxy/VIP with an epoch check. Promotion without fencing is a split-brain machine.
3. **Application layer.** The email should never have outrun durability: send it via the outbox pattern inside the order's transaction, so an order that does not survive also never emails.
4. **Detection.** A reconciliation comparing confirmation events against order rows would have caught this in minutes instead of via customer complaints.

The framing to end on: RPO for an OLTP system is a *choice* — async replication chooses RPO > 0, and you must either accept and reconcile, or pay latency for RPO = 0.

### Q17: You're designing multi-region active-active for a user-profile service. Which writes conflict, how do you resolve them, and where do you refuse to go active-active?

**Answer:** Classify the data first, because active-active is a per-field decision, not a service-level one:

- **Single-writer fields** (display name, avatar — written by one user, usually one device): conflicts are rare and LWW with a hybrid/logical timestamp is acceptable — the newest human intent should win, and the "loser" was the same human seconds earlier.
- **Sets** (blocked users, favorites): use an OR-Set CRDT so concurrent add and remove from two regions merge with add-wins semantics, rather than one region's change silently vanishing.
- **Counters** (followers, karma): PN-Counters or region-sharded counters summed on read — LWW on a counter is data loss by design.
- **Where I refuse active-active:** anything with a global uniqueness or balance invariant — username claims, email changes, payment methods, money. Uniqueness cannot be merged after the fact (two regions both grant `@alice`); it needs a single serialization point: home-region ownership per key (route username claims to a home region and pay cross-region latency on that one flow) or a strongly consistent multi-region mode (Spanner-style, or DynamoDB global tables' strong-consistency mode).

Then the operational half: version vectors or per-field timestamps in the replication stream; conflict-resolution metrics on a dashboard (silent LWW resolution hides product bugs); a documented merge per field; and read-your-writes via session-sticky routing so a user who just edited in region A does not read region B's stale copy. The sentence that scores: consistency requirements attach to *invariants*, not to services — split the data by invariant and give each class the cheapest mechanism that preserves it.

### Q18: A cron leader elected via etcd ran a data migration twice, corrupting a table, even though etcd never had two lease holders. How?

**Answer:** The lock service being correct does not make the system correct — this is the stale-holder gap. Timeline: instance A acquires the etcd lease and leadership and begins the migration; A stalls — a long GC pause, a VM live-migration, an EBS hiccup — long enough that its lease expires because keep-alives stopped; etcd, correctly, lets the lease die; instance B acquires leadership, sees the migration incomplete, and starts it; A then resumes mid-loop, unaware it lost the lease (its last check was before the pause), and both write. etcd never had two concurrent holders — but there were two concurrent *actors*, because A's knowledge was stale, and check-then-act over a network is never atomic. Fixes, in order of strength:

1. **Fencing at the resource.** Every write from the migration carries the etcd key revision (or lease/term) as a fence, and the database rejects lower fences — `UPDATE ... WHERE fence <= :token` semantics, or a `migration_runs` row holding the token with all writes conditional on it.
2. **Idempotent, resumable migration.** Checkpointed batches keyed by range, each batch an upsert — a double-run then converges instead of corrupting.
3. **Hygiene that narrows but never closes the window.** Re-check the session between batches; stop work on lease loss. Useful, but a pause can always fit between the check and the write — so (1) and (2) are the correctness story.

This is the most reliable staff-level litmus test in the whole section: "the lease expired but the holder kept acting — what saves you?" The answer must live at the data layer.

### Q19: Kafka consumers in a payments pipeline are lagging. Someone proposes raising `max.poll.records` and adding partitions. What do you interrogate first?

**Answer:** First, *why* the lag — is throughput genuinely insufficient, or is the consumer group churning? Frequent rebalances (processing exceeding `max.poll.interval.ms`, GC pauses missing heartbeats, rolling deploys) collapse throughput without any real capacity problem, and raising `max.poll.records` makes that *worse* by lengthening the poll loop. Check, in order: rebalance frequency; per-partition lag skew (one hot partition — a single large merchant as the key — means added partitions will not help, because ordering is per-key and the hot key still lands on one partition); and downstream latency (if each record makes a 50 ms synchronous PSP call, the fix is batching, pipelining, or in-consumer concurrency, not more partitions). Then the correctness interrogation before any scaling change: adding partitions changes the key→partition mapping for new messages, breaking per-key ordering across the transition — if the pipeline relies on "all events for payment X arrive in order," you need a planned cutover (drain, or a dual-read window), not a live bump. And if consumers scale out, verify processing is idempotent, because more consumers plus rebalances means more redelivery — a payments pipeline amplifying at-least-once into double effects is a worse incident than lag. Only after all that: partitions sized generously up front (you cannot shrink), `max.poll.records` tuned so a full batch always completes within `max.poll.interval.ms`. The signal the interviewer wants: scaling knobs are easy; the candidate who asks "what breaks ordering and idempotency when I turn them?" is the one who has run payments infrastructure.

### Q20: Design failure detection and automated failover for a stateful service so that the automation itself can't cause the outage.

**Answer:** Principle first: a failure detector in an asynchronous network can only *suspect* — it cannot distinguish dead from slow from partitioned — so every automated action must be safe when the detector is wrong. Design:

1. **Quorum-based detection.** No single health-checker gets to declare death (a checker partitioned from a healthy primary is the classic false-positive failover — GitHub 2018). Require agreement from multiple vantage points, ideally the same quorum that authorizes the failover, and use adaptive suspicion (phi-accrual) over fixed timeouts so thresholds track real network behavior.
2. **Fenced promotion.** Promotion is an atomic epoch increment through a consensus store (etcd, or the cluster's own Raft): the new primary's epoch invalidates the old one, and clients/proxies reject the old epoch. Even if the "dead" primary was merely slow, its writes bounce — split-brain is prevented by fencing, not by hoping detection was right.
3. **Rate limits and hysteresis on the automation.** At most one automated failover per window, cooldowns between actions, and a circuit breaker on the remediation itself: if failovers keep triggering, stop and page a human — repeated automated failover is the signature of a gray failure or a detector bug amplifying itself, and several famous large outages were automation storms, not the original fault.
4. **Blast-radius caps.** Automation refuses to act if it would remove more than K% of capacity: a detector that suddenly suspects half the fleet is describing a network problem or its own failure, not fifty simultaneous machine deaths.
5. **Gray-failure inputs.** Feed client-observed error and latency (outlier detection) into the decision, not just liveness probes, and compare failover candidates against their peers before promoting onto equally sick hardware.

Close with the design stance: the goal is not perfect detection — that is impossible — but making every wrong decision recoverable and rate-limited. Fencing makes wrong failovers *safe*, hysteresis makes them *rare*, and blast-radius caps make them *small*.
