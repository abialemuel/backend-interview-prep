# Core Concepts

## Ansible philosophy

Four properties define Ansible:

1. **Agentless** — no software is installed on managed hosts. The control node connects over SSH (Linux) or WinRM (Windows); modules are small Python snippets shipped to the target, executed, and removed.
2. **Idempotent** — re-running a converged playbook is a no-op. Modules report `changed` or `ok`, and only `changed` tasks trigger downstream handlers.
3. **Declarative YAML** — you describe the desired state (`state: present`, `enabled: true`) and let the module figure out how to get there.
4. **Push-based** — the control node initiates the connection, rather than agents polling a central server. This is the opposite of Chef/Puppet's pull model and removes the need for a central server at all.

The downside: the control node must be able to reach every target over SSH, and large inventories can be slow without `forks` tuning, SSH pipelining, or the `free` strategy.

A currency note: as of mid-2026 the current engine is **ansible-core 2.19** (shipped in Ansible community package 12). 2.19's headline change was a rewritten templating engine with far better error messages and stricter handling of untrusted/tagged data — worth knowing because it broke some sloppy Jinja constructs that older playbooks relied on.

## Inventory

Inventory is the list of hosts Ansible manages. Static inventory lives in INI or YAML; dynamic inventory is generated by a plugin or script.

```ini
# inventory/production.ini
[web]
web1.example.com ansible_host=10.0.0.10
web2.example.com ansible_host=10.0.0.11

[db]
db1.example.com ansible_host=10.0.0.20

[prod:children]
web
db

[prod:vars]
ansible_user=ubuntu
ansible_ssh_private_key_file=~/.ssh/prod.pem
```

```yaml
# inventory/production.yml — YAML form, equivalent
all:
  children:
    prod:
      children:
        web:
          hosts:
            web1.example.com: { ansible_host: 10.0.0.10 }
            web2.example.com: { ansible_host: 10.0.0.11 }
        db:
          hosts:
            db1.example.com: { ansible_host: 10.0.0.20 }
      vars:
        ansible_user: ubuntu
        ansible_ssh_private_key_file: ~/.ssh/prod.pem
```

Group nesting via `[group:children]`, group-scoped vars via `[group:vars]`, and host-scoped vars inline. For non-trivial values, split into `group_vars/<group>.yml` and `host_vars/<host>.yml` files, which Ansible auto-loads.

### Dynamic inventory

For cloud environments static files are wrong — hosts come and go. Use a dynamic inventory plugin:

```yaml
# inventory/aws_ec2.yml
plugin: amazon.aws.aws_ec2
regions: [us-east-1, us-west-2]
keyed_groups:
  - prefix: tag_env
    key: tags.Environment
  - prefix: tag_role
    key: tags.Role
filters:
  tag:Environment: [prod, staging]
hostnames: [private-ip-address]
compose:
  ansible_user: "'ec2-user'"
```

The plugin queries the AWS API at run time and returns groups like `tag_env_prod`, `tag_role_web`. AWS, GCP, Azure, VMware, OpenStack, and many others ship inventory plugins as collections.

## Ad-hoc commands

```bash
ansible web -i inventory/production.ini -m ansible.builtin.command -a "uptime"
ansible web -m ansible.builtin.shell -a "df -h | grep /var"
ansible web -m ansible.builtin.ping
ansible web -m ansible.builtin.yum -a "name=htop state=present" -b
```

Ad-hoc commands run a single module against a host pattern. Useful for one-off operations and for sanity-checking inventory and connectivity. `-b` becomes root; `-m` selects the module; `-a` passes args.

## Modules

Modules are the unit of work. They ship as `namespace.collection.module` (e.g. `ansible.builtin.yum`, `community.docker.docker_container`). Builtins live under `ansible.builtin.*` and ship with `ansible-core`.

Frequently used builtins:

| Module | Purpose |
| --- | --- |
| `ansible.builtin.command` | run a command without shell processing (no pipes, no env) |
| `ansible.builtin.shell` | run a command through `/bin/sh`, supports pipes and redirects |
| `ansible.builtin.file` | file/directory state, mode, owner, symlink |
| `ansible.builtin.copy` | copy a file from control node to target |
| `ansible.builtin.template` | render a Jinja2 template and copy it |
| `ansible.builtin.yum` / `ansible.builtin.apt` | package management |
| `ansible.builtin.git` | clone/pull a repo |
| `ansible.builtin.systemd` | service state and enablement |
| `ansible.builtin.user` | user/group management |
| `ansible.builtin.service` | generic service management |
| `ansible.builtin.lineinfile` / `ansible.builtin.blockinfile` | surgical edits to existing files |
| `ansible.builtin.stat` | inspect a file |
| `ansible.builtin.setup` | gather facts |

### Idempotency and how modules achieve it

Idempotency means a converged task reports `ok` (not `changed`) on subsequent runs. Builtins achieve it by checking current state first: `yum name=htop state=present` queries the package manager; if `htop` is installed, the module returns `ok` without invoking `yum install`. `template` compares the rendered content to the destination and only writes (and reports `changed`) when they differ. `systemd state=started enabled=true` checks the unit's running and enabled state and only acts if needed. The `command` and `shell` modules are NOT idempotent by default — they run every time — which is why you reach for the declarative module first and use `creates`/`removes` arguments or `when` conditions to make `command` safe.

## Playbook structure

```yaml
- name: Configure web servers
  hosts: web
  become: true
  become_user: root
  vars:
    app_version: "1.4.2"
  tasks:
    - name: Install nginx
      ansible.builtin.yum:
        name: nginx
        state: present

    - name: Render site config
      ansible.builtin.template:
        src: site.conf.j2
        dest: /etc/nginx/conf.d/site.conf
        mode: "0644"
      notify: reload nginx

    - name: Ensure nginx is enabled and running
      ansible.builtin.systemd:
        name: nginx
        state: started
        enabled: true

  handlers:
    - name: reload nginx
      ansible.builtin.systemd:
        name: nginx
        state: reloaded
```

A **play** maps a set of hosts to a list of **tasks**. `become: true` enables privilege escalation (sudo by default); `become_user` selects the target user. Tasks run top-to-bottom across all hosts in lockstep by default (the `linear` strategy). Each task has a `name` (shown in output and used for `--start-at-task`), a module call, and optional `vars`/`when`/`loop`/`register`/`tags`/`notify`.

## Variables and facts

Variables come from inventory (`group_vars`, `host_vars`, inline), `vars` in the play, `vars_files`, role defaults, role vars, `set_fact`/`include_vars`, and extra-vars on the CLI. Precedence is documented and extensive — roughly: CLI `--extra-vars` wins, then role vars, then play vars, then inventory, then role defaults at the bottom.

**Facts** are variables Ansible gathers about each host at the start of a play via the `setup` module: OS family, architecture, network interfaces, mounted filesystems, CPU, memory, etc. They are namespaced under `ansible_*` (e.g. `ansible_os_family`, `ansible_eth0.ipv4.address`). Disable gathering with `gather_facts: false` for speed when you do not need them. **Custom facts** live in `/etc/ansible/facts.d/*.fact` on the target and appear under `ansible_local.*`, useful for embedding host metadata.

```yaml
tasks:
  - name: Print OS family
    ansible.builtin.debug:
      msg: "This is a {{ ansible_os_family }} box"
```

## Templates — Jinja2

`ansible.builtin.template` renders a `.j2` file through Jinja2 and copies it. Jinja2 gives filters, tests, conditionals, and loops.

```
# templates/nginx.conf.j2
upstream app {
{% for host in groups['web'] %}
  server {{ hostvars[host]['ansible_eth0']['ipv4']['address'] }}:8080;
{% endfor %}
}

server {
  listen 80;
  server_name {{ app_fqdn | default('localhost') }};
  root {{ doc_root | default('/var/www/html') }};

{% if enable_tls | bool %}
  ssl on;
  ssl_certificate {{ tls_cert_path }};
{% endif %}

  location / {
    proxy_pass http://app;
    proxy_set_header X-Forwarded-For {{ remote_addr | default('') }};
  }
}
```

Filters: `default`, `to_json`, `from_json`, `regex_replace`, `b64decode`, `map`, `selectattr`, `groupby`, `sort`, `unique`, `json_query`. Tests: `defined`, `success`, `failed`, `changed`, `string`, `number`.

## Conditionals and loops

```yaml
- name: Install Apache on RHEL family
  ansible.builtin.yum:
    name: httpd
    state: present
  when: ansible_os_family == "RedHat"

- name: Install Apache on Debian family
  ansible.builtin.apt:
    name: apache2
    state: present
  when: ansible_os_family == "Debian"

- name: Create users
  ansible.builtin.user:
    name: "{{ item.name }}"
    groups: "{{ item.groups | default(omit) }}"
    shell: /bin/bash
  loop: "{{ users }}"

- name: Create config directories
  ansible.builtin.file:
    path: "/etc/app/{{ item.key }}"
    state: directory
  with_dict: "{{ app_config }}"
```

`loop` is the modern form; `with_items`, `with_dict`, `with_fileglob`, `with_nested` are older loop-style helpers that still work but `loop` plus filters covers most cases. `when` accepts booleans, Jinja comparisons, and lists (`when: x and y`).

## Handlers

Handlers are tasks notified by other tasks and run only when the notifier reports `changed`. They are flushed at the end of the play (or at `meta: flush_handlers`) and deduplicated — notifying `reload nginx` three times runs it once.

```yaml
tasks:
  - name: Copy nginx config
    ansible.builtin.template:
      src: nginx.conf.j2
      dest: /etc/nginx/nginx.conf
    notify: reload nginx

handlers:
  - name: reload nginx
    ansible.builtin.systemd:
      name: nginx
      state: reloaded
```

This avoids restarting a service on every run; it restarts only when its config actually changed.

## Roles

A role is the standard unit of reuse — a packaged directory of tasks, handlers, vars, defaults, files, templates, and metadata that you apply to a host group via `roles:` or `include_role`.

```
roles/nginx/
  defaults/main.yml    # default variable values (lowest precedence, overridable)
  vars/main.yml        # role vars (higher precedence, intended to be fixed)
  tasks/main.yml       # the task list
  handlers/main.yml    # handlers
  files/               # static files for copy
  templates/           # Jinja2 templates for template
  meta/main.yml        # role metadata, dependencies, supported platforms
```

```yaml
- hosts: web
  become: true
  roles:
    - role: nginx
      vars: { nginx_workers: 4 }
    - role: geerlingguy.redis
```

`ansible-galaxy init roles/nginx` scaffolds the directory structure. Roles are published to Ansible Galaxy and consumed via `requirements.yml`:

```yaml
# requirements.yml
roles:
  - name: geerlingguy.redis
    version: 1.8.0
```

## Collections

Since Ansible 2.10 the distribution model is **collections** — versioned, namespaced bundles of modules, roles, and plugins (`community.aws`, `community.docker`, `ansible.posix`, `google.cloud`). Builtins live under `ansible.builtin` in `ansible-core`. Install with:

```bash
ansible-galaxy collection install community.docker:3.10.0
```

```yaml
# requirements.yml
collections:
  - name: community.aws
    version: 8.0.0
  - name: ansible.posix
```

Modules from collections are referenced by their fully qualified name (`community.docker.docker_container`) to avoid collisions and make source explicit.

## ansible.cfg

```ini
[defaults]
inventory = inventory/production.ini
remote_user = ubuntu
private_key_file = ~/.ssh/prod.pem
host_key_checking = False
forks = 20
stdout_callback = yaml
retry_files_enabled = False
roles_path = roles:~/.ansible/roles
collections_path = ~/.ansible/collections

[privilege_escalation]
become = True
become_method = sudo
become_user = root
```

`ansible.cfg` is searched up the tree (current dir, home, `/etc/ansible/ansible.cfg`) and configures defaults, callbacks, connections, and privilege escalation. Environment variables (`ANSIBLE_*`) override it.

## Vault

`ansible-vault` encrypts variables and whole files with AES-256. Use it for secrets that must live alongside playbooks.

```bash
ansible-vault encrypt group_vars/prod/vault.yml
ansible-vault edit group_vars/prod/vault.yml
ansible-vault view group_vars/prod/vault.yml
ansible-vault decrypt group_vars/prod/vault.yml
```

Run playbooks with `--ask-vault-pass` or `--vault-password-file ~/.vault_pass.txt`. For team use, store the vault password in a shared secret store (Bitwarden, 1Password, AWS Secrets Manager) via a vault password client script. For serious deployments, integrate with external secret stores instead of vault files — look up secrets at runtime from AWS Secrets Manager, HashiCorp Vault, or similar via lookup plugins (`amazon.aws.aws_secret`), so they never touch disk in plaintext.

## Tags

```yaml
- name: Install nginx
  ansible.builtin.yum: { name: nginx, state: present }
  tags: [packages, web]

- name: Render config
  ansible.builtin.template: { src: nginx.conf.j2, dest: /etc/nginx/nginx.conf }
  tags: [config, web]
```

`--tags config --skip-tags packages` runs only the tagged subset. Useful for partial runs during debugging and for splitting long playbooks into rerunnable sections.

## Check mode, diff mode, syntax check

```bash
ansible-playbook site.yml --syntax-check     # parse, do not run
ansible-playbook site.yml --check            # dry run; modules report changed but do nothing
ansible-playbook site.yml --check --diff     # dry run plus before/after diffs for templated files
ansible-playbook site.yml --check --diff --limit web1.example.com
```

`--check` is the Ansible equivalent of `terraform plan`: modules simulate the change and report `changed` but do not act. Some modules (notably `command`/`shell`) cannot check and are skipped. `--diff` shows line-level diffs for `template`, `lineinfile`, `file` mode changes, etc. Always `--syntax-check` in CI.

## Strategies

- **linear** (default) — each task runs to completion across all hosts before the next task starts. Simple, predictable, but slow with heterogeneous hosts (the slowest host gates every task).
- **free** — each host runs through all tasks as fast as it can without waiting. Faster but tasks across hosts are out of order, so it is unsafe when hosts depend on each other.

Configure per-play with `strategy: free` or globally in `ansible.cfg`. For raw throughput the first levers are `forks` (default 5) and SSH `pipelining = True`; the Mitogen plugin used to be the classic speed answer but lags modern ansible-core versions, so check compatibility before citing it. For rolling deploys, `serial: 25%` runs the play in batches and `max_fail_percentage` aborts if too many hosts in a batch fail — the built-in canary mechanism.

## Execution environments and the platform landscape

The modern way to run Ansible in CI and at scale is inside an **execution environment (EE)** — a container image bundling ansible-core, a Python interpreter, collections, and their Python/system dependencies. EEs solve the "works on my laptop" problem of control-node dependency drift: the same image runs locally (via `ansible-navigator`), in CI, and on the platform. `ansible-builder` builds them from a declarative `execution-environment.yml`.

The landscape above the CLI:

- **AWX** — the upstream open-source web UI/API/scheduler (job templates, RBAC, credential storage, inventory syncing).
- **Red Hat Ansible Automation Platform (AAP, 2.6 as of late 2025)** — the supported product: automation controller (downstream AWX), private automation hub (curated collections), **Event-Driven Ansible**, and **Ansible Lightspeed** (AI assistant, now with bring-your-own-model support). AAP 2.6 also added OPA-based **policy as code** to enforce organizational rules on job execution.
- **Event-Driven Ansible (EDA)** — rulebooks (`ansible.eda`) subscribe to event sources (webhooks, Kafka, Prometheus/alertmanager, cloud events) and trigger playbooks when conditions match. This flips Ansible from human-initiated push to automated remediation: "when the disk-full alert fires, run the cleanup playbook." A common 2026 interview topic for ops-heavy roles.

## Testing and linting

- `ansible-lint` — the standard static analyzer: catches deprecated syntax, non-FQCN module names, missing `name`s, risky `command` use, and enforces best-practice profiles. Run it in CI on every PR.
- `ansible-playbook --syntax-check` and `--check --diff` — parse and dry-run; cheap CI gates.
- **Molecule** — the role-testing framework: spins up ephemeral test instances (Docker/Podman by default), applies the role, runs verifications, and — critically — runs the role **twice** to assert idempotency (second run must report zero changes). The Ansible analog of `terraform test`.

## Ansible vs Terraform

The classic contrast is **configuration management vs provisioning** and **mutable vs immutable infrastructure**.

| | Ansible | Terraform |
| --- | --- | --- |
| Domain | Configure existing hosts, deploy apps, orchestrate | Provision cloud resources (VMs, VPCs, DBs, IAM) |
| Model | Mutable — mutates hosts in place over time | Immutable-ish — replaces resources when config changes |
| Style | Mostly imperative execution of declarative tasks | Declarative end-state with diff |
| State | Stateless — no central source of truth | Stateful — `terraform.tfstate` maps config to reality |
| Idempotency | Module-level, opt-in (`state: present`) | Built-in via state refresh + diff |
| Transport | SSH/WinRM push | Provider API calls |
| Best for | OS config, package install, app deploy, ad-hoc ops | Cloud resource lifecycle |

In practice they compose: Terraform provisions the VM, network, and database; Ansible configures the OS, installs packages, and deploys the application on top. The mutable/immutable split is the interview-relevant framing: Ansible mutates existing hosts, Terraform replaces resources. In a fully immutable pipeline (e.g. Packer-built AMIs deployed by Terraform), Ansible's role shrinks to the Packer build step.
