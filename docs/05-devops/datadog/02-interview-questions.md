# Datadog Interview Questions

Grading: **Easy** = junior (core observability vocabulary), **Medium** = mid/senior (instrumentation and alerting ownership), **Hard** = senior/staff (architecture, cost, and trade-off judgment).

## Easy (junior)

### Q1: What are the three pillars of observability?
**Answer:** Metrics, logs, and traces. Metrics are numeric time series — cheap, aggregatable, good for dashboards and alerts ("error rate is 2%"). Logs are discrete events with full context — good for debugging the specific failing request ("the order failed because user X had a null billing address"). Traces are trees of spans showing a request's path across services — good for understanding where time and errors come from in a distributed system. Datadog implements all three and correlates them via shared tags and `trace_id` so you can pivot from a metric spike to the logs and traces of the requests that caused it.

### Q2: Observability vs monitoring?
**Answer:** Monitoring is the act of collecting signals and alerting on them; observability is a property of the system — can you understand its internal state from its external outputs? A system with only `cpu_usage` and `request_count` is monitored but not observable, because you cannot slice by `user_id` or `tenant_id` to find the specific population affected by a problem. The practical test for observability is high cardinality: can you group by arbitrary dimensions (user, tenant, feature flag, build SHA) without pre-aggregating? Datadog supports that via tags, which is why tag discipline is the most important habit.

### Q3: When do you use metrics vs logs vs traces?
**Answer:** Metrics for dashboards and alerts over time — they are cheap, aggregatable, and answer "what is the overall error rate / latency / throughput?" Logs for debugging a specific event — they answer "what happened for this failing request?" and carry full context. Traces for understanding a request's path across services — they answer "where did the time go, and which service errored?" in a distributed system. Use all three: a metric alert tells you something is wrong, a trace tells you which service is responsible, a log tells you why.

### Q4: What does the Datadog Agent do?
**Answer:** The Agent is a daemon on each host (or a sidecar/DaemonSet) that collects host metrics and events, forwards logs and traces from applications, and runs integration checks against services like postgres, nginx, and kubelet. Applications send custom metrics via dogstatsd and traces via the tracer library to the Agent, which batches and ships them to Datadog. On Kubernetes the Cluster Agent talks to the API server for metadata and provides an admission controller that can auto-inject the tracer and standard tags into pods. Without the Agent you only get cloud-provider metrics, not host-internal or application-level signals.

### Q5: What metric types does Datadog support?
**Answer:** GAUGE (a value at a point in time), COUNT (accumulated since last flush), RATE (a count normalized to per-second), HISTOGRAM (agent-side percentiles stored as separate p50/p95/p99/max metrics), and DISTRIBUTION (raw values sent to Datadog, server-side percentiles that support arbitrary group-by at query time). HISTOGRAM locks the aggregation at submission time — you cannot later slice its p95 by a tag you did not submit per-tag. DISTRIBUTION is more flexible but costs more to ingest. Use HISTOGRAM when you know the groupings in advance, DISTRIBUTION when you need flexible slicing.

### Q6: What is dogstatsd?
**Answer:** dogstatsd is a statsd-compatible protocol (UDP or Unix domain socket) by which applications submit custom metrics to the Datadog Agent. You call `statsd.increment("api.requests", tags=["endpoint:/checkout"])` from your code; the Agent listens on `127.0.0.1:8125` (or a UDS socket for lower overhead), aggregates, and flushes to Datadog every ~10 seconds. UDS is preferred over UDP for high-throughput apps because it avoids packet loss. Custom metrics submitted via dogstatsd are billed per unique tag combination, so tag by dimensions you will aggregate over, not by unique identifiers.

## Medium (mid/senior)

### Q7: Why do tags matter, and what is the cardinality cost problem?
**Answer:** Tags are how you slice and aggregate metrics at query time — `avg:http.request.latency{service:api,env:prod} by version`. They are the source of observability: without a `user_id` or `tenant_id` tag you cannot find which population a problem affects. The cost trap is high cardinality: each unique tag combination is a separate stored time series, and Datadog bills custom metrics per unique combination per month. Tagging every request with `request_id` creates millions of series and explodes your bill. Tag by dimensions you will actually aggregate over (`service`, `env`, `version`, `endpoint`), not by unique identifiers; use DISTRIBUTION metrics for flexible slicing.

### Q8: What is a span and a trace?
**Answer:** A span is a unit of work — an HTTP handler, a DB query, a downstream call — with a start time, duration, service, operation, resource, and tags. A trace is a tree of spans linked by parent/child relationships representing one request's path through the system; the root span is the entry point and child spans are nested operations. A trace might have a root `GET /checkout` span with children for a postgres query, an HTTP call to the pricing service, and a Kafka publish. The tree shape is what lets you see which downstream call dominated the request.

### Q9: How does distributed tracing context propagate across services?
**Answer:** The trace context — `trace_id`, `parent_span_id`, sampling decision — is injected into outbound request headers by the tracer library and extracted on the inbound side. Datadog uses `x-datadog-trace-id`, `x-datadog-parent-id`, and `x-datadog-sampling-priority`; OpenTelemetry uses the W3C `traceparent`/`tracestate` headers (or B3 for Zipkin compatibility). For HTTP, gRPC, Kafka, and most message brokers the libraries handle injection/extraction automatically; for custom transports you must propagate manually. If a service does not propagate, the trace breaks at that hop and you get two disconnected traces.

### Q10: Head-based vs tail-based sampling — and why is tail-based powerful for errors?
**Answer:** Head-based sampling decides at the root span whether to sample; the decision propagates in the headers, so either the whole trace is sampled or none of it. Simple and consistent, but the decision is made before the request completes, so at a 0.1% sample rate you rarely catch the 0.01% of requests that error. Tail-based sampling buffers the complete trace at the Agent and decides whether to keep it based on the full picture — errors, high latency, specific tags. Datadog uses tail-based sampling by default for APM, which is why it can guarantee 100% of error traces are captured even at a low overall sample rate. That is the killer feature for troubleshooting.

### Q11: How are traces, logs, and metrics correlated?
**Answer:** Every span carries a `trace_id`; the Datadog log library injects `@trace_id` and `@span_id` into log records when configured (via a log formatter or MDC). In the UI you click a slow span and pivot to "logs for this trace" or "metrics for this service" — same time window, same tags. The `trace_id` is the join key that turns the three pillars into one workflow. The same tags (`service`, `env`, `version`) are applied across metrics, logs, and traces so a dashboard query and a log query and a trace query all slice the same way.

### Q12: Automatic vs custom instrumentation?
**Answer:** Datadog's tracer libraries auto-instrument popular frameworks and libraries (Express, Django, Flask, Rails, Spring, gin, net/http, psycopg, AWS SDK) with zero code changes — you get HTTP and DB spans out of the box. Custom instrumentation adds spans or tags for business logic the auto-instrumentation cannot see — a `checkout.process_order` span with `user_id` and `cart_size` tags. The rule: rely on auto-instrumentation for the framework/DB layer; add custom spans only for business-critical paths and add tags you will query later. Tags are where the observability of traces comes from.

### Q13: What is a Datadog monitor and what types exist?
**Answer:** A monitor is an alert on a query. Types include metric (threshold on a metric query), anomaly (deviation from a learned baseline via forecasting), outlier (a group whose behavior diverges from peers), forecast (predict when a metric will cross a threshold, e.g. disk fill), composite (boolean combination of other monitors), log (alert on a log query count or pattern), and trace analytics (alert on APM metrics like error rate or p95). Each monitor has alert and warning thresholds, multi-alert over tag groups (alert per service or per env), and a templated notification message routed to PagerDuty, Slack, email, or webhooks.

### Q14: SLOs and error budgets?
**Answer:** An SLO is a target on a service's reliability over a window — "99.9% of checkout requests succeed over 30 days." Datadog computes SLOs from metric monitors (success/total ratio) or from log/trace queries and tracks the error budget — how many bad events you can still afford within the window before breaching. A burn-rate alert says "at this rate you will breach in 2 hours," which is more actionable than a raw error-rate alert because it accounts for the remaining budget. SLOs turn monitoring into a product-level conversation rather than a per-signal one.

## Hard (senior/staff)

### Q15: Anomaly detection — how does it work and when is it useful?
**Answer:** Anomaly monitors use forecasting to learn a metric's expected baseline (including seasonality — daily/weekly patterns) and alert when actual values deviate beyond a configurable sensitivity. They are useful when a fixed threshold is wrong because the metric naturally varies by time of day or day of week — e.g. traffic spikes during business hours, so a static "requests > 1000" alert fires constantly at 9am and never at 3am. The trade-off is that anomaly alerts can be noisier and harder to tune than threshold alerts; use them for "something is unusual" signals and keep plain threshold alerts for well-understood SLOs.

### Q16: Synthetic monitoring vs RUM?
**Answer:** Synthetic monitoring runs scheduled API or browser tests from managed locations — a check that hits your health endpoint every minute from 12 regions and alerts on non-200 or latency regression. It tests from the outside, on a schedule, whether you have traffic or not, so it catches outages before users do. RUM (Real User Monitoring) collects performance and error data from real user browsers and mobile apps — page load timing, frontend errors, XHR latency, session replay. It shows what actual users experienced. RUM correlates with backend traces via the `trace_id` injected into XHR headers, so a user-reported "checkout is slow" can pivot from the RUM session to the backend trace that served it.

### Q17: Log parsing and cost control — how do you keep log spend sane?
**Answer:** Logs are the most expensive Datadog signal, billed by GB ingested and by volume retained in indexes. Levers: drop noisy logs at the Agent before they count against ingestion (Agent `log_processing_rules` with exclude matchers); tier indexes by retention (ERROR hot, WARN shorter, INFO minimal, DEBUG archived to S3 only); move high-volume, rarely-queried logs (audit, security) to the Flex Logs tier, which decouples cheap long-term storage from query compute; parse raw logs into structured facets via pipelines and grok so you can query without re-scanning; generate log-based metrics for alerting so you alert on a metric count rather than scanning logs at query time; and archive cold logs to S3 for long-term retention without index cost. The discipline is: ingest only what you will query, parse it once, and tier the rest.

### Q18: OpenTelemetry and vendor neutrality — when use it with Datadog?
**Answer:** OpenTelemetry is the CNCF vendor-neutral standard for instrumentation — by 2026 the default choice for new services — and Datadog ingests it three ways: OTLP straight to the Agent, a standalone OTel Collector with the Datadog exporter, or DDOT, Datadog's supported distribution of the OTel Collector embedded in the Agent, which accepts OTel-native pipelines while keeping Agent features. The advantage is vendor neutrality — you are not locked into Datadog's tracer libraries and can switch backends (Tempo, Honeycomb, the Grafana stack) by changing an exporter. The trade-off is that native libraries still have richer auto-instrumentation in some ecosystems and the tightest integration with profiling and log-correlation injection. The pragmatic compromise: instrument with the OTel SDK and semantic conventions, export via OTLP/DDOT, keep Datadog as the backend, and preserve the option to leave.

### Q19: The cluster agent and admission controller?
**Answer:** On Kubernetes the Cluster Agent runs as a Deployment and talks to the API server for metadata, while DaemonSet Agents on each node collect pod metrics and traces. The Cluster Agent enriches pod metrics with labels/annotations and aggregates cluster-level metrics. The admission controller is a webhook that can auto-inject the Datadog tracer library and standard tags (`env`, `service`, `version`) into pods at creation, so you get tracing without modifying every deployment's Docker image or YAML. It is the recommended path for tracing on Kubernetes because it standardizes tags across services and removes the per-app tracer-installation burden.

### Q20: AWS integration auth — how does Datadog get AWS data?
**Answer:** You create an IAM role that Datadog assumes via AWS STS, with a trust policy allowing Datadog's AWS account to assume it, and a permissions policy granting read access to EC2, CloudWatch, CloudTrail, and the services you integrate. The Agent (or the cloud integration) pulls EC2 host metadata, CloudWatch metrics, and CloudTrail events using that role. For high-volume CloudWatch metrics, use Kinesis Firehose to stream metrics directly to the Datadog intake instead of the older polling model, which avoids per-API-metric cost and is the recommended pattern. The role's least-privilege scope matters — grant only the read permissions Datadog needs.

### Q21: Alerting best practices — how do you avoid alert fatigue?
**Answer:** Alert on symptoms that matter to users (error rate, latency, SLO burn rate) rather than on every resource metric (CPU > 80%); use multi-alert monitors grouped by `service` and `env` tags so one alert fires per affected group instead of one global alert; tune thresholds against real data and use anomaly or outlier monitors where static thresholds do not fit; route alerts to the right team via service tags so the on-call for `service:billing` gets billing alerts; use warning vs alert tiers so a warning can be paged only if it persists; and silence noisy monitors during known maintenance windows. The goal is a small number of actionable alerts — every alert should map to a runbook and a human action.

### Q22: How would you instrument a PHP or Go service for Datadog?
**Answer:** Install the tracer library — for PHP the `dd-trace-php` extension (auto-instrumenting Laravel/Symfony/Doctrine/guzzle with zero code changes); for Go the `dd-trace-go` package imported and started at process boot with `tracer.Start()` and `tracer.Stop()` at exit. Rely on auto-instrumentation for the framework/DB layer. Add custom spans for business-critical paths (`tracer.StartSpan("checkout.process_order")`) and tags you will query later (`user_id`, `tenant_id`, `feature_flag`, `cart_size`). Submit custom metrics via dogstatsd (`statsd.Incr("api.requests", []string{"endpoint:/checkout"}, 1)`). Configure the log formatter to inject `trace_id` so logs and traces correlate. Set standard tags (`env`, `service`, `version`) via env vars or the tracer config so dashboards slice consistently across services. A strong 2026 answer also mentions the alternative: instrument with the OTel SDK instead and export OTLP to the Agent, trading some Datadog-native depth for portability.

### Q23: Define SLI, SLO, SLA, and error budget — and how do you choose good SLIs?
**Answer:** An SLI is the measurement: a ratio of good events to total events, e.g. successful checkout requests over all checkout requests, or requests under 300ms over all requests. An SLO is the internal target on that SLI over a window ("99.9% over 30 days"); an SLA is the external contract with penalties, always looser than the SLO. The error budget is the inverted SLO — 99.9%/30d allows about 43 minutes of full downtime — and it governs the ship-vs-stabilize trade: budget remaining means keep shipping, budget exhausted means reliability work takes priority. Good SLIs measure user-visible symptoms at the service boundary (availability, latency, correctness of responses), not causes (CPU, memory, pod restarts); a handful per service, defined where users experience them. The senior tell is connecting the budget to decision-making rather than reciting definitions.

### Q24: Why are multi-window burn-rate alerts the standard way to alert on SLOs?
**Answer:** Alerting on the raw SLI threshold either pages too eagerly (a brief blip at 99.8% is fine when you have a month of budget) or too late (a slow bleed never crosses the instant threshold but exhausts the budget). Burn rate normalizes this: burn rate 1 means consuming exactly your budget over the window; burn rate 14 means burning through it 14x too fast. Multi-window pairs a fast window (e.g. 5m/1h at high burn rate) that catches sudden outages within minutes, with a slow window (e.g. 6h/3d at low burn rate) that catches gradual degradation, and each alert requires both the short and long window to breach so a transient spike doesn't page. This is the Google SRE workbook pattern; Datadog SLO monitors implement it directly. The payoff: pages correlate with real risk of breaching the SLO, which is the definition of an actionable page.

### Q25: Datadog vs an open-source stack (Prometheus + Grafana + Loki/Tempo + OTel) — how do you argue the choice?
**Answer:** Frame it as build-vs-buy on total cost and correlation quality. Datadog: one platform, one tagging model, out-of-the-box correlation between metrics/logs/traces, 900+ integrations, hosted reliability, plus products the OSS stack lacks (synthetics, RUM, DBM, SIEM) — at a price that grows with hosts, custom-metric cardinality, and log volume, with lock-in mostly at the instrumentation and dashboard/alert layer. OSS: no license cost but real engineering cost — you operate Prometheus federation/Thanos, Loki, Tempo, Grafana, and alerting yourself, and correlation across signals is yours to build; it wins on data sovereignty, cost predictability at very large scale, and Kubernetes-native shops with platform teams. OpenTelemetry is the hedge either way: instrument once with OTel and the backend becomes swappable. Staff-level answers name a threshold — small teams buy, large platform teams with steady-state scale can justify building — and mention negotiating Datadog cost levers before migrating.

### Q26: What does observability for LLM-backed features add beyond classic APM?
**Answer:** Classic APM tells you the request succeeded in 800ms; for an LLM feature that is table stakes, because the response can be fast, 200-OK, and wrong. LLM observability adds: traces over prompt chains and agent/tool-call steps (which retrieval, which tool, which model call), token usage and per-request cost as first-class metrics, model/prompt version as tags so regressions attribute to the change, and quality signals — evaluation scores, hallucination/guardrail flags, user feedback — alongside latency and errors. Datadog ships this as LLM Observability, and the same shape exists in OTel semantic-convention work (GenAI conventions) for the vendor-neutral path. The interview point: the new failure modes are semantic (bad answers) and economic (token cost blowups), so you must instrument quality and cost, not just latency and status codes.
