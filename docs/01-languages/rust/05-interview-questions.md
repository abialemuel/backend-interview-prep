# Interview Questions

## How to use this file (grading)

Questions are grouped by difficulty, and each group maps to an expectation level:

- **Easy — junior.** Any candidate who's written Rust for a few months should answer these cold.
- **Medium — senior.** Expected depth for someone shipping Rust in production; interviewers probe the "why," not just the "what."
- **Hard — senior/staff.** A staff-level answer connects the mechanism to a production or design decision — costs, failure modes, and what they'd flag in code review or an architecture doc. The gap between senior and staff here is rarely "knows more Rust trivia" — it's "knows when Rust was the right call and can defend the trade-off."

Answer aloud first, then compare with the model answer.

## Easy

### Q1: What are the three rules of ownership?
**Answer:** (1) Each value has exactly one owner — a variable binding. (2) There can only be one owner at a time; assigning or passing a non-`Copy` value **moves** ownership, and the previous binding becomes invalid. (3) When the owner goes out of scope, the value is dropped automatically — its destructor runs and its memory is freed. These three rules, enforced entirely at compile time, are what let Rust guarantee no use-after-free and no double-free without a garbage collector.

### Q2: What's the difference between `&T` and `&mut T`, and what rule governs how many of each can exist at once?
**Answer:** `&T` is a shared, immutable reference; `&mut T` is an exclusive, mutable reference. At any point in the code, you may have either any number of `&T` references, or exactly one `&mut T` reference — never both kinds at once to the same data. This is the compiler's core aliasing rule, and it's what prevents data races: you can't have one thread reading while another writes, because you can't even have two references that would allow it to compile.

### Q3: What's the difference between `String` and `&str`?
**Answer:** `String` is an owned, heap-allocated, growable UTF-8 string — you own the data and are responsible for it being dropped. `&str` is a borrowed *string slice*: a pointer plus a length pointing into UTF-8 data owned by someone else (a `String`, a string literal embedded in the binary, or another `&str`). Function parameters should generally accept `&str` (it accepts both a borrowed `String` via deref coercion and a string literal), while owned data you're storing or returning as a new value should be `String`.

### Q4: Why doesn't Rust have null, and what replaces it?
**Answer:** Null pointers are the source of an entire class of runtime crashes in languages that have them (Tony Hoare famously called inventing null his "billion-dollar mistake"). Rust has no null value for any ordinary type; the absence of a value is represented explicitly by the `Option<T>` enum (`Some(T)` or `None`). Because `Option<T>` is a distinct type from `T`, the compiler statically forces you to handle the `None` case — via `match`, `if let`, or a combinator like `.unwrap_or()` — before you can access the inner value. A null-pointer dereference simply cannot happen in safe Rust; the compiler won't let you write the code.

### Q5: What's the difference between `Option<T>` and `Result<T, E>`, and when do you use each?
**Answer:** Both are two-variant enums the compiler forces you to handle exhaustively. `Option<T>` (`Some`/`None`) models the presence or absence of a value with no explanation needed for absence — a lookup that might not find anything, an optional config field. `Result<T, E>` (`Ok`/`Err`) models success or failure *with information about the failure* — anything that can fail for a reason the caller might want to inspect, log, or branch on (I/O, parsing, network calls). If you find yourself wanting to say *why* something is `None`, that's a signal it should have been a `Result` instead.

### Q6: What does `#[derive(...)]` do, and name three traits it's commonly used with.
**Answer:** `#[derive(...)]` is a procedural macro attribute that auto-generates a trait implementation based on a type's structure, so you don't hand-write boilerplate. Common ones: `Debug` (enables `{:?}` formatting for debugging output), `Clone` (enables `.clone()` for an explicit deep copy), and `PartialEq` (enables `==`/`!=` comparison). Others frequently seen: `Default` (a zero-argument constructor with sensible defaults), `Serialize`/`Deserialize` (from `serde`, for JSON/etc. conversion), and `Hash` (usable as a `HashMap` key). Deriving only works when every field's type also implements the trait being derived.

## Medium

### Q7: Why does this fail to compile?
```rust
fn main() {
    let s1 = String::from("hello");
    let s2 = s1;
    println!("{s1}");
}
```
**Answer:** `let s2 = s1` **moves** ownership of the heap-allocated `String` from `s1` to `s2`, because `String` doesn't implement `Copy` (copying it would mean either an implicit deep copy the language doesn't want to hide, or two owners of the same heap allocation, which Rust's single-owner rule forbids). After the move, `s1` is no longer a valid binding — using it is a compile error: `value borrowed here after move`. The fix is either to use `s2` instead of `s1`, or to call `s1.clone()` on the second line if you genuinely need two independent, owned copies.

### Q8: A teammate's PR fails to compile with a borrow-checker error on this code — what's wrong, and how do you fix it?
```rust
fn main() {
    let mut v = vec![1, 2, 3];
    let first = &v[0];
    v.push(4);
    println!("{first}");
}
```
**Answer:** `first` is an immutable borrow of `v`, and it's still in use at the `println!` on the last line — so its lifetime spans across `v.push(4)`, which requires a mutable borrow of `v`. The compiler rejects mixing an active immutable borrow with a mutable one, and the reason is concrete, not pedantic: `push` might need to reallocate `v`'s backing buffer to fit the new element, which would leave `first` pointing at freed memory — exactly the dangling-pointer bug the borrow checker exists to prevent. The fix: use `first` before the mutation, or clone the value out (`let first = v[0];`, which copies the `i32` instead of borrowing it) if you need it to outlive the mutation.

### Q9: Explain `Send` and `Sync`, and why `Rc<T>` implements neither.
**Answer:** `Send` means a type is safe to move to another thread; `Sync` means a type is safe to access via `&T` from multiple threads concurrently. Both are auto-derived marker traits with no methods — the compiler implements them automatically for a type if all of its fields are `Send`/`Sync`. `Rc<T>` maintains its reference count with a plain, non-atomic integer for performance, since it's designed for single-threaded shared ownership; two threads calling `Rc::clone` concurrently would race on that counter. Because `Rc<T>` doesn't implement `Send`, the compiler refuses to compile code that moves one into a spawned thread — the fix is `Arc<T>`, which uses an atomic reference count at a small extra cost.

### Q10: When would you choose `dyn Trait` over a generic type parameter, and what do you give up?
**Answer:** Choose `dyn Trait` when you need a heterogeneous collection (`Vec<Box<dyn Shape>>` holding different concrete types behind one interface), a plugin-style extension point where the concrete type isn't known until runtime, or when you want to avoid the compile-time and binary-size cost of monomorphizing a function over many call sites. You give up: a runtime vtable-indirection cost per call (small but real, and it defeats inlining across the call), and the requirement that the trait be **object-safe** (no generic methods, no methods returning `Self` by value). Generics remain the default for library-internal, performance-sensitive code where the concrete types are known at compile time — static dispatch is exactly as fast as hand-written non-generic code.

### Q11: What's the difference between cloning an `Rc<T>` and cloning a `Vec<T>`?
**Answer:** `Rc::clone(&rc)` (or `rc.clone()`) increments an internal reference count and returns a new pointer to the *same* heap allocation — cheap, no deep copy, and the data is only actually dropped once every `Rc` clone has been dropped. `vec.clone()` on a `Vec<T>` allocates an entirely new backing buffer and copies every element into it — an O(n) deep copy, and the two `Vec`s are then completely independent. Interviewers ask this because `.clone()` looking identical at the call site for both types is a common source of confusion for engineers coming from languages where clone always means one specific thing.

### Q12: Explain the `?` operator and what happens when the function's error type differs from the error being propagated.
**Answer:** `?`, applied to a `Result`, either unwraps the `Ok` value and continues execution, or returns early from the enclosing function with the `Err` value. If the error type in the enclosing function's `Result<T, E>` differs from the error type being propagated, `?` calls `From::from` to convert it — which is exactly what `#[from]` on a `thiserror` enum variant generates automatically. If no `From` conversion exists between the two error types, using `?` there is a compile error, not a runtime one: the compiler catches unhandled error-type mismatches before the program ever runs, unlike an unchecked exception that only surfaces the mismatch when it's actually thrown.

### Q13: Why is `Arc<Mutex<T>>` such a common pattern in Rust backend code, and what's its single-threaded equivalent?
**Answer:** Sharing mutable state across threads needs two things: shared ownership (so the data outlives any single thread that's using it) and synchronized access (so only one thread mutates at a time). `Arc<T>` provides the first (atomic reference counting, safe to clone across threads); `Mutex<T>` provides the second (exclusive access via a lock, and crucially, the `Mutex` in Rust *owns* the data it protects, so you cannot touch it without holding the guard — unlike Go, where the mutex and the protected data are separate fields and nothing stops you from reading the field unlocked). The single-threaded equivalent, when you need shared ownership and interior mutability but never cross a thread boundary, is `Rc<RefCell<T>>` — cheaper (no atomics, no locking, just a runtime borrow-flag check that panics on violation instead of blocking).

### Q14: When is it acceptable to call `.unwrap()` in production code?
**Answer:** When you can prove, from the surrounding code's own invariants, that the `None`/`Err` case is unreachable — e.g., indexing into a `Vec` you just checked isn't empty, or parsing a string literal you wrote yourself. Even then, `.expect("why this can't fail")` is preferred over bare `.unwrap()`, because the message becomes the panic output and documents the assumption for whoever hits it later if the assumption turns out to be wrong. It is *not* acceptable on anything derived from external input, I/O, or a network call in a request-handling path — that turns an operational failure (a malformed request, a timed-out call) into a full panic, which in most web frameworks kills or degrades the handling of that request instead of returning a proper error response.

## Hard

### Q15: Rust vs Go — when and why would you choose Rust for a new backend service?
**Answer:** Choose Rust when the service is genuinely bottlenecked on the language runtime itself, and you've either measured that or can predict it with confidence: hard p99/p999 latency requirements where a GC pause of even a couple of milliseconds is unacceptable, CPU- or memory-bound workloads (a proxy, a serialization/parsing hot path, an ingestion pipeline) where profiling would show the GC or interface-boxing overhead as a real cost, or a target that has no GC option at all (WASM, embedded, a kernel module). Choose Go — or default to whatever your team already runs — for the much larger remainder of backend work: services bottlenecked on a database round trip or a downstream API, CRUD business logic, anything where developer velocity, compile-time iteration speed, and hiring pool size matter more than shaving the last few percent of latency or memory. The realistic adoption pattern at companies actually doing this (Discord, Cloudflare) is not "rewrite everything" — it's Go or another GC'd language for the API layer and business logic, Rust for the one or two subsystems where the trade-off is clearly worth its cost. A staff-level answer names the concrete axis the decision turns on (latency SLO, CPU/memory cost at scale, or a GC-incompatible target) rather than reaching for "Rust is faster/safer" as a blanket claim.

### Q16: You're implementing an LRU cache with a hash map plus a doubly-linked list for eviction order. Why is this notoriously hard to write in safe Rust, and how do people actually solve it?
**Answer:** A doubly-linked list needs each node to hold a reference to both its neighbors — but the borrow checker's single-owner, no-cyclic-mutable-aliasing model has no natural way to express "two nodes each mutably reference each other." Modeling it directly with `&mut` references produces borrow-checker errors that don't have a clean fix, because the structure genuinely requires shared, mutable access to the same nodes from multiple places. In practice, this is solved one of three ways: (1) don't use a linked list at all — back the LRU order with an index into a `Vec`/slab and swap-remove, or use an existing crate (`lru`) that's already solved it; (2) use `Rc<RefCell<Node>>` for the links, accepting the runtime borrow-check cost and the reference-counting overhead; (3) drop to `unsafe` with raw pointers between nodes, exactly how `std::collections::LinkedList` itself is implemented internally, and wrap it behind a safe public API. The interview-relevant point: hitting a wall with the borrow checker on a genuinely cyclic data structure isn't "doing Rust wrong" — it's a known, named class of problem with known, named solutions, and reaching for `unsafe` there is a textbook-legitimate use, not a red flag, as long as it's small and wrapped safely.

### Q17: Explain how `async`/`await` actually executes, and why holding a `MutexGuard` across an `.await` point is dangerous.
**Answer:** An `async fn` compiles to a state machine implementing the `Future` trait; nothing runs until an executor calls `poll()` on it, and each `.await` is a potential suspension point where the state machine can pause and let the executor run something else. Holding a `std::sync::MutexGuard` (a *blocking* mutex guard) across an `.await` keeps that lock held for the entire duration of whatever the await is waiting on — if that's a network call, you've turned a fast, in-memory critical section into a lock held for however long the network takes, and every other task needing that lock queues up behind it, which can cascade into a latency spike or an effective deadlock under load. There's a second, sharper problem: a blocking `MutexGuard` held across an await can make the enclosing future non-`Send` in some cases, since the executor may need to move a suspended task between worker threads and the guard's internals may not support that — this surfaces as a confusing compile error on `tokio::spawn`, not a runtime symptom. The fix is either to scope the guard tightly so it's dropped before the `.await` (reacquire it after), or to use `tokio::sync::Mutex`, whose async-aware `.lock().await` doesn't block a worker thread while waiting — it yields to the executor instead. `clippy::await_holding_lock` flags this pattern automatically.

### Q18: What discipline do you apply around `unsafe` code in review, and what's actually being promised when you write it?
**Answer:** `unsafe` doesn't disable the type checker or the borrow checker for the surrounding code — it unlocks exactly five specific operations (raw pointer dereference, calling an `unsafe fn`, mutable statics, `unsafe trait` impls, union field access) that the compiler cannot verify are sound, and by writing it you are personally attesting that you've upheld the invariants it would otherwise check: no data races, no dangling or misaligned pointers, no aliasing violations, no reads of uninitialized memory. In review, the standard I'd apply: the `unsafe` block should be as small as possible (ideally a few lines, not a whole function body), it should be wrapped behind a safe public API so callers can't misuse it, and there should be a comment directly above it stating the specific invariant being relied on — "safe because `idx < self.len` was checked above" — so a future reader (including future-you) doesn't have to re-derive the safety argument from scratch. `cargo miri test` is worth running on any code exercising raw pointers, since Miri can catch categories of undefined behavior that neither a passing test suite nor `cargo test` would ever surface, precisely because UB doesn't reliably manifest as a crash.

### Q19: A service has 500,000 goroutines-worth of concurrency (a Go mental model) mapped onto Rust with `tokio`. What tuning knobs matter, and what's the closest Rust equivalent to `GOMAXPROCS`?
**Answer:** Tokio's multi-threaded runtime defaults `worker_threads` to the number of visible CPUs — the direct analog of Go's default `GOMAXPROCS`, and in a containerized environment it's just as important to check that the container's CPU limit (cgroup quota) is what the runtime actually sees, for the same reason `GOMAXPROCS` needed a container-aware fix in Go: an over-provisioned worker-thread count relative to the actual CPU quota causes scheduling overhead and context-switch churn instead of real parallelism. Unlike a goroutine (2 KB starting stack, genuinely cheap to spawn in huge numbers), a tokio task's overhead per instance is higher — each is a heap-allocated future plus whatever state it captures — so "500,000 concurrent tasks" needs to be checked against actual memory budget, not assumed cheap by analogy. The other knob with no Go equivalent at all: since there's no automatic preemption of a task that never hits an `.await`, a single CPU-bound or accidentally-blocking task can starve an entire worker thread — this is why `spawn_blocking`'s separate blocking-thread pool exists, and sizing that pool (`max_blocking_threads`, default 512) matters independently of `worker_threads`.

### Q20: Design a high-throughput event-ingestion service in Rust — say, ingesting millions of events/sec from a message broker, validating them, batching, and writing to storage. Where does ownership help, and where does it get in your way?
**Answer:** A reasonable shape: a small pool of `tokio` tasks each own a broker consumer partition and pull raw messages; each message is parsed and validated (returning `Result<Event, ValidationError>` so malformed input never panics the ingestion path); valid events are pushed into a bounded `mpsc` channel per batching worker, providing backpressure if storage falls behind the broker's produce rate; batching workers accumulate events up to a size or time threshold and flush a batch to storage (object storage, a columnar sink, a database) using owned, `'static` data throughout, so no batch borrows anything from the consumer task that produced it.

**Where ownership helps:** the type system makes the pipeline's data-flow contract explicit and enforced — once a message is parsed into an owned `Event`, nothing else can be silently mutating it out from under a batching worker, because passing it down the channel *moves* it; there's no reference-counted, garbage-collected object floating between stages that something else might still be holding onto. Validation failures are `Result`, not exceptions, so a malformed event is a normal, cheap, non-panicking data-flow branch, not an unwind. And because there's no GC, the batching hot loop has no pause risk at all — throughput is bounded by actual CPU/IO work, not by an unpredictable collector pause under memory pressure at exactly the wrong moment (a real risk at "millions of events/sec" scale in a GC'd language).

**Where it gets in the way:** a shared, mutable "in-flight batch" structure that multiple tasks want to append to concurrently (rather than each task owning its own batch and flushing independently) pushes you toward `Arc<Mutex<Batch>>` or a lock-free structure, and getting the lock scope right — not held across the actual flush I/O — takes real care given the async-mutex-across-await pitfall from Q17. Backpressure design (bounded channel sizes, what happens when a batching worker falls behind) has to be decided explicitly up front, because ownership being moved through a channel means there's no implicit shared buffer to fall back on if you didn't design one. And if the service later needs a plugin-style extensibility point — "let downstream teams register a custom validator" — that's exactly the `dyn Trait` heterogeneous-collection case from Q10, trading a little dispatch overhead for not having to know every validator's concrete type at compile time. None of this is unsolvable; it's the same category of design decision you'd make in Go with channels and mutexes, but Rust makes you make it explicitly and up front, rather than letting a shared mutable map quietly work "well enough" until it doesn't.
