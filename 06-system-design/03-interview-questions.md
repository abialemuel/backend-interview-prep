## System Design Interview Questions

Use these for self-testing. For each question, try to answer out loud — pace and structure matter at least as much as content — before reading the model answer. Design prompts follow the structured approach from the README: requirements, high-level, key components, scaling, trade-offs.

## Easy

### Q1: What is the difference between vertical and horizontal scaling?

**Answer:** Vertical scaling (scale up) adds resources — CPU, RAM, larger instance class — to a single machine. It is simple, preserves a single coherent state, and requires no code changes, but it has a hard physical ceiling and the machine is a single point of failure. Horizontal scaling (scale out) adds more machines behind a load balancer; it scales without bound in principle and is fault-tolerant by construction, but it forces you to partition or replicate state and to reason about distributed consistency. The practical answer for most workloads is both: a vertically scaled primary for writes, a horizontally scaled stateless fleet for compute, and read replicas or shards for read scale. Scale vertically until you cannot, and start scaling horizontally before you have to.

### Q2: Why does statelessness enable horizontal scaling?

**Answer:** A stateless service has no per-instance state the next request depends on — sessions live in a shared store (Redis, JWT, encrypted cookie) rather than in process memory. That means any instance can serve any request, so you can add or remove instances freely to match load, deploys do not risk dropping in-flight user sessions, and the load balancer can use any routing algorithm. As long as state lives on the app server, you cannot reschedule or restart instances without breaking the user's session, so you lose the main benefit of horizontal scale. The first refactor most monoliths make is extracting session state into a shared store precisely so the app tier can become stateless.

### Q3: What is the difference between an L4 and an L7 load balancer?

**Answer:** An L4 load balancer operates on the transport layer — TCP/UDP flows identified by IP and port — and cannot inspect the application payload. It is fast, cheap, and protocol-agnostic, so it is typically used for internal service traffic or database connections (e.g., AWS NLB, HAProxy in TCP mode). An L7 load balancer operates on HTTP/gRPC; it can route by URL, host, header, or cookie, terminate TLS, rewrite requests, and shape traffic by content (e.g., AWS ALB, nginx, Envoy). L7 is more expensive and a larger attack surface but is the standard for public web tiers. The right answer is usually L7 at the public edge, L4 for internal east-west between services.

### Q4: Explain the database scaling path.

**Answer:** The typical path is: single primary (all reads and writes; bounded by one box), then read replicas that stream binlog/WAL asynchronously (reads scale, writes do not, replicas lag so the read path becomes eventually consistent), then sharding by a key like user_id or tenant_id (writes scale too, but cross-shard queries become expensive and the shard key is nearly impossible to change later), then denormalization (duplicate data into read-optimized tables so reads become single-shard lookups, paying with write amplification), and finally specialized NoSQL stores for hot workloads (DynamoDB for key/value at scale, Elasticsearch for search, a column store for analytics). Each step buys a dimension of scale and incurs a cost; the order is a default, not a rule.

### Q5: What is the difference between availability and reliability?

**Answer:** Availability is the fraction of time the system is able to serve a request — expressed in nines (99.9% ≈ 43 minutes downtime per month). Reliability is the probability the system produces a correct result over a period; a system can be highly available but return wrong data, in which case it is not reliable. Durability is a third related term — the probability your data survives over time even if the system is temporarily unavailable (S3's 11 nines are durability). Each nine beyond the third costs roughly an order of magnitude more engineering effort, so design for the SLA the business actually needs, not for "five nines everywhere."

### Q6: State the latency numbers every backend engineer should know.

**Answer:** L1 cache ≈ 0.5 ns; main memory reference ≈ 100 ns; SSD random read ≈ 100 μs; within-data-center round trip ≈ 0.5 ms; HDD seek ≈ 10 ms; cross-continent network round trip ≈ 150 ms. The relationships matter more than the digits: RAM is about 1000× faster than SSD, SSD about 1000× faster than HDD, and a within-DC call is milliseconds while a cross-region call is hundreds of milliseconds. These ground your capacity estimates ("if I have to fan out to 10 services, that is 5 ms minimum, plus DB time") and your caching arguments.

## Medium

### Q7: Explain CAP and PACELC.

**Answer:** CAP says that during a network partition (P) you must choose either consistency (every read sees the latest write, or an error) or availability (every request gets some non-error response, possibly stale) — you cannot have both. Because partitions are unavoidable in real networks, you cannot have all of C, A, and P. CP systems block during a partition (etcd, ZooKeeper, synchronous MySQL failover); AP systems keep serving and accept staleness (DynamoDB eventually consistent, multi-region active-active). PACELC extends this: partitions are rare, and in the steadystate (Else) you trade latency (L) against consistency (C). MySQL synchronous replication is PC/EL — slow writes, eventually consistent reads. Spanner is PC/EC — globally strongly consistent at high latency. DynamoDB is PA/EL — fast and available, eventually consistent. PACELC explains real production trade-offs where CAP alone is silent.

### Q8: What consistency models exist, and which do real systems use?

**Answer:** Strong consistency (linearizability) gives every read the most recent write in a single total order; it requires quorum or synchronous replication and constrains replica placement. Sequential consistency preserves a total order per client but not real-time order. Causal consistency preserves the order of causally related operations while allowing concurrent operations in any order — captured by vector clocks. Eventual consistency converges only after writes stop; with no bound on "eventually." Session consistency (read-your-writes) is a common pragmatic subset: a session never sees an older version of data the same session wrote. In practice, the write path of a typical CRUD app (Laravel + MySQL + Redis) is strong (single primary serializes writes), the read path is eventually consistent (replicas lag), and the cache is eventually consistent with the DB (delete on write misses are racy). Naming the boundaries explicitly is the interview skill.

### Q9: Compare cache-aside, read-through, write-through, and write-behind.

**Answer:** Cache-aside (lazy loading) lets the application check the cache, read the DB on a miss, and write the value back; resilient to cache failure, but cold-key reads are slow and the cache can be stale until TTL. Read-through moves the read-miss logic into the cache itself via a provider, simplifying app code; requires the cache to know how to load. Write-through synchronously updates the cache and the DB on a write — the cache is never stale but write latency is now cache-write + DB-write, and a cache failure implies a write failure (durability coupled to availability). Write-behind (write-back) returns from the cache and flushes to the DB asynchronously — write latency is cache-only, but durability is at risk if the cache dies before the flush. Match the pattern to the workload: cache-aside for the general read-heavy case, write-through for must-be-fresh hot data, write-behind only for copious low-value writes or counters, or when paired with strong cache persistence.

### Q10: What is a cache stampede, and how do you prevent it?

**Answer:** A cache stampede (thundering herd) is when many concurrent requests all miss the same expiring key at once, all hit the DB simultaneously to repopulate it, and the DB gets a spike it was not sized for; each request independently repopulates the cache. Fixes: a mutex/lock so only the first request repopulates and others wait or serve stale (Redis `SETNX` or `singleflight` in Go), probabilistic early expiration (XFetch) where each request near TTL randomly decides to refresh early, smearing the refresh load across the last part of TTL, and request coalescing where concurrent missers share a single in-flight load. Often combined: lock + serve-stale, so users see a slightly stale value while one request refreshes.

### Q11: Differentiate cache penetration, breakdown, and avalanche, with fixes.

**Answer:** Penetration is when clients ask for keys that never existed, so every request misses, hits the DB, and returns nothing to cache — fix by caching negative results with a short TTL or by putting a Bloom filter in front of valid keys (no false negatives). Breakdown is a single hot key expiring and a burst immediately overwhelming the DB — fix with a mutex, no-expiry-plus-async-refresh for known hot keys, or logical expiration with stale-while-revalidate. Avalanche is many keys expiring at the same wall-clock time (e.g., a deploy that warmed everything with TTL=3600) — fix by randomizing TTLs with ±10-20% jitter, warming the cache before traffic exposure, and circuit-breaking the DB if it starts failing. The fixes differ; you cannot fix avalanche with a bloom filter.

### Q12: Why is cache invalidation "the hardest problem," and what do you do about it?

**Answer:** The cache is a second copy of every value, and keeping it coherent with the source of truth is the difficulty — every write must somehow invalidate (or update) the right cache keys, and missing one leaves stale data until TTL. Update-on-write has a race where interleaved writes produce a stale value that lives forever (delete-on-write is preferred because deletes are idempotent and order-insensitive). But even delete is racy when a read is in flight that started before the DB write but its SET happens after the delete — that read repopulates the cache with the old value. Mitigations: TTL as a backstop, delayed double-delete, event-driven invalidation via CDC, and versioned keys (embed a version in the key so new writes miss the old key by construction). The transactional outbox pattern makes invalidation durable across cache downtime.

### Q13: Why is idempotency essential for retries?

**Answer:** Clients and queues will retry — a timed-out call returns, the caller retries, the original succeeded in the meantime — and without idempotency you get double charges, duplicate rows, double email sends. Idempotency is the property that calling twice has the same effect as calling once. Implement with idempotency keys (Stripe-style: client sends a key per logical operation, server replays the stored response on retry), unique constraints or `INSERT IGNORE` so duplicate writes harmlessly fail, conditional writes (`UPDATE ... WHERE version = ?`) so only the first retry succeeds, and dedup tables for cross-system effects. Because message brokers deliver at-least-once and the network always eventually fails, idempotency is mandatory, not optional.

### Q14: Compare the saga pattern with two-phase commit.

**Answer:** Two-phase commit (2PC) is the classic distributed transaction protocol: a coordinator asks each participant to prepare, and if all prepare, instructs them to commit. It blocks during the prepare phase, is fragile to coordinator failure, and is almost unusable at internet scale. The saga pattern instead sequences local transactions across services; each step has a compensating action that semantically undoes it. If step 4 fails, run the compensations of steps 1-3 in reverse. There is no global isolation, so intermediate states are visible and you design the UX around it (e.g., "payment processing"). Sagas come in two flavors: orchestration (a central orchestrator calls each step; explicit flow, but the orchestrator can become a god service) and choreography (each service reacts to events and emits the next; no central coordinator but the flow is implicit). Most shops orchestrate the main business workflow and choreograph side-effects. 2PC is avoided at scale because its costs outweigh its benefits.

### Q15: What is the outbox pattern, and what problem does it solve?

**Answer:** The outbox pattern solves the dual-write problem — when a service must update its database and publish an event, simply doing both in sequence is not atomic: the Kafka call can fail, or the service can crash between the two. The outbox writes the DB row and an outbox row in the same transaction, so the event is durable as soon as the transaction commits; a separate process (often binlog CDC via Debezium, or a poller) reads the outbox and publishes to the broker, then marks rows as published. The event cannot be lost. Delivery is at-least-once, so consumers must be idempotent. Side benefits: you get a free event log, replay capability, and you avoid the dual-write consistency bug entirely. It is the industry-standard way to reliably publish domain events from a transactional system.

### Q16: Compare synchronous and asynchronous inter-service communication.

**Answer:** Synchronous communication (REST, gRPC) is simple and immediate, but couples the caller's latency and availability to the callee — a chain N services deep multiplies failure probability, and one slow dependency can hold all your worker threads. Asynchronous communication (Kafka, SQS, EventBridge, NATS) decouples them: the producer publishes and returns, the consumer processes when it can, and the producer does not need to know who consumes. It also enables fan-out — one event serves many subscribers. The trade-off: a new infrastructure layer (the broker), at-least-once delivery semantics requiring idempotent consumers, and the fact that the work is not done synchronously, so the user-facing synchronous flow must be designed around the pending state. In practice, the common pattern is sync for user-critical logic (you cannot return 200 to "place order" without accepting it) and async for everything off the critical path.

### Q17: Explain circuit breakers, bulkheads, retries, and timeouts.

**Answer:** These are the resilience patterns every cross-service call needs. A **timeout** caps how long a call can hang so a slow downstream cannot hold all your workers; **retries with exponential backoff and jitter** recover from transient failures without amplifying load (no jitter means all clients retry in lockstep, a thundering herd of retries); a **circuit breaker** stops calling a service that is failing — it opens after a threshold of failures, returns immediately, and after a cooldown allows a probe request to close. A **bulkhead** isolates resources per dependency — separate thread/connection pools per downstream — so a slow payments service cannot exhaust the connections orders needs to call inventory. Together they prevent cascading failure: timeout bounds the damage, retry recovers from transient issues without overdoing it, circuit breaker stops beating a dead downstream, and bulkhead ensures one bad dependency cannot starve the others.

### Q18: When should you NOT use microservices?

**Answer:** When the team is small enough that the operational overhead exceeds the scaling benefit; when the system is not actually growing or under distinct scaling pressure; when an organizational reorg would solve the team-boundary problem you are trying to solve technically; when latency is the primary non-functional requirement and one in-process call sequence would do; and when you do not yet know the bounded contexts of your domain. Premature splitting locks in a guess — you only learn the right service boundaries after living with the system for a while. The common advice is to start as a monolith and extract when the boundaries are stable and the pressure is real, using the strangler fig pattern to incrementally pull services out. A distributed monolith — services that are split but coupled on data — has all the costs of microservices and none of the benefits.

## Hard

### Q19: What is an API gateway, and what is a BFF? When do you use each?

**Answer:** An API gateway sits at the edge as the single front door for external clients, handling TLS termination, authentication, rate limiting, routing, response caching, and transformation — examples include Kong, AWS API Gateway, NGINX, and Envoy. A backend-for-frontend (BFF) is a per-frontend backend: one for the web app, one for iOS, one for Android, each aggregating downstream services into a response shape tailored to that frontend. The BFF is aggregation and shaping, not business logic — it lets a mobile client render one screen with one round trip instead of fifteen, and lets each frontend team ship without coordinating with the others. You use the API gateway always (everyone has the cross-cutting concerns it handles), and a BFF when frontends have diverged enough that a one-size-fits-all API forces over-fetching and round-trip explosion. Some shops implement BFFs as Lua/GraphQL inside the gateway itself.

### Q20: How does DDD bounded context inform microservices boundaries?

**Answer:** DDD's bounded context is the unit of decomposition — each context has its own ubiquitous language and its own model of the same reality. "Customer" means different things to Billing (identity + payment method) and to Shipping (address + delivery preferences), so forcing them to share one Customer model causes friction. A microservice should own one bounded context. Signs you have it wrong: every change requires coordination across services (boundary too split), teams keep asking for data they do not own (boundary in the wrong place), or a single service keeps growing without limit (you extracted too little). The worst outcome is a distributed monolith — services split but coupled on data, requiring coordinated deploys for any change. Boundaries must be designed from the domain, not from technical layers (do not split into a "user service" and "auth service" — split into "accounts" and "billing").

### Q21: Briefly describe event sourcing and CQRS, and when you would use them.

**Answer:** Event sourcing stores the log of changes (events) as the source of truth, instead of a mutable current state; current state is a projection folded from the events, allowing full audit history, replay, and the derivation of new read models. CQRS (Command Query Responsibility Segregation) separates the write model (commands) from one or more read models optimized for the queries they serve. They pair well: an event-sourced write model feeds multiple CQRS read projections. Use them when the read shape diverges dramatically from the write shape (leaderboards, search indices, time-series analytics) or when audit and replay are first-class requirements. They add real complexity — large event logs, eventual consistency of projections, schema evolution of events — so do not adopt them by default. For most CRUD apps, a relational store with a couple of denormalized read tables is simpler and sufficient.

### Q22: Design a URL shortener.

**Answer:** Requirements: short, unique, durable URLs with low-latency redirects; high read:write ratio (say 10:1); 100M new URLs/month and 1B reads/month, peaking ~10x. High-level: client hits the shortener at `s.example/abc123`; a service resolves the long URL and 301-redirects (301 for permanent, cacheable; 302 for analytics-on-every-click trade-off). Key components: an API to mint codes, a Redis cache keyed by short code, a MySQL primary storing `(short_code, long_url, created_at, owner)`, read replicas, a worker for analytics ingestion via a queue. ID generation: either base62-encode an auto-increment/`Snowflake` ID, or hash the long URL and truncate; collisions are possible with hashing so use a try-and-retry or counter-based strategy. Scaling: cache aggressively (90%+ hit rate given the read skew); shard by short code prefix once a single primary saturates; CDN redirects for hot codes. Trade-offs: 301 vs 302 (cacheable vs analytics-fresh), counter-vs-hash uniqueness (collision vs sequential), single primary vs sharding (simpler vs capacity).

### Q23: Design a rate limiter.

**Answer:** Requirements: per-client limit (e.g., 1000 req/hour), distributed across multiple app instances, low added latency, configurable per route. Choose a strategy: **token bucket** (a bucket gains tokens at a fixed rate, consumes one per request — allows bursts up to the bucket capacity; the most flexible); **fixed window** (a counter per `(client, window)` — simple but bursts at window edges); **sliding window log** (precise but memory-heavy); **sliding window counter** (approximate via two adjacent windows, well-balanced). A token bucket in Redis is the standard: `INCR` with `EXPIRE`, or a Lua script for atomic decrement+seed. The algorithm runs behind a middleware; on limit exceeded, return 429 with `Retry-After`. Trade-offs: in-memory limiter is fast but per-instance (cannot limit globally), Redis is shared but adds a round trip and a failure mode — mitigate with a local allowance or fail-open vs fail-closed decision when Redis is down. Multi-level: per-user at the edge (CDN/gateway), per-IP at the LB, per-tenant in-app.

### Q24: Design Twitter's timeline.

**Answer:** Requirements: a user sees a reverse-chronological feed of posts from followees; 10M DAU, ~100 refreshes/day each, ~50 posts per refresh; reads dominate ~100:1. High-level: posts land in a `posts` table; the feed is the set of recent posts from a user's followees. Key decision — **fan-out on write** vs **fan-out on read**. Fan-out on write precomputes each follower's feed at post time (fast reads, but a celebrity with 10M followers produces 10M feed writes per post). Fan-out on read computes the feed by blending followee timelines at fetch time (cheap writes, slow heavy reads). Hybrid: fan-out on write for typical users, fan-out on read for celebrities, choosing per-post based on a cached follower count. Store precomputed feeds as Redis sorted sets scored by timestamp; cache aggressively with a staleness budget. Scaling: shard posts by user_id, cache the hot fraction, use read replicas for the blended-read fallback. Trade-offs: latency vs storage cost, freshness vs cost, eventual consistency between write and appearance in feeds.

### Q25: Design a notification system.

**Answer:** Requirements: deliver notifications across channels (email, SMS, push, in-app) on events; respect user preferences; never duplicate; tolerate third-party outages. High-level: an `events` topic (Kafka) is published by domain services; a notifier service consumes events, expands user preferences into channel-specific tasks, enqueues each into a per-channel queue (SES for email, SNS/Twilio for SMS, FCM for push), and workers call the third-party with retry + backoff. Components: preferences store, user device registry for push, a templates store, a dead-letter queue for perma-failed sends. Idempotency is essential — dedupe per `(event_id, channel, recipient)` in a `notification_log` table with a unique constraint, so retries from upstream or redelivery from the broker cannot produce duplicate deliveries. Scaling: per-channel queue isolates a slow SMTP gateway from a healthy push path; the workers autoscale per queue depth. Trade-offs: at-least-once delivery vs exactly-once display (the latter requires dedup); latency vs cost (batch sends vs immediate); retry vs alert the user by a fallback channel.

### Q26: Design a distributed cache.

**Answer:** Requirements: shared, low-latency key/value read path across a fleet of app instances; tunable consistency; survives node loss; line-rate throughput. High-level: a cluster of cache nodes where keys are partitioned by consistent hashing (so adding or removing a node only moves ~1/n of the keys, not all of them). Each node owns a shard; replication across N nodes per key for availability; a gossip-based membership/clustering layer (Redis Cluster, Memcached with client-side hashring + replicas). Key components: client library that knows the topology, a consistent-hash ring with virtual nodes to spread load evenly, a failover mechanism that picks a replica when the primary owner dies. Read path: hash key -> find owner -> GET; on miss, the caller loads from DB and writes back (cache-aside semantics). Write path: invalidate via delete on the owner and replicas. Scaling: more shards for throughput, more replicas for read scale and availability, hot-key subsharding (split a key into N keys picked at random). Trade-offs: consistency (a write to the owner and a stale read from a lagging replica) vs availability; sharding adds capacity but breaks multi-key operations; in-process caching as a layer above reduces load on the shared cluster but introduces per-instance staleness. Eviction policy: LRU/LFU/TinyLFU based on the access pattern; TTL as the backstop.
